# yamaa 0.5.0

yamaa 0.5.0 is in development on the `release/0.5.0` branch; the plan is
#2785. These notes grow with each merged change and are finished before the
release is qualified.

## Install

0.5.0 will be distributed the same way as 0.4.0, as assets of the GitHub
release tagged `yamaa-v0.5.0`, unless #2785 records a different decision.

The Linux wheel is `manylinux_2_34` and needs glibc 2.34 or later, for example
RHEL 9, Ubuntu 22.04 or Debian 12; older systems build from
`yamaa-0.5.0.tar.gz`.

### Source packages

- The installed R package carries only the test inputs that its installed
  suites read, so it is about 5 MB smaller on Linux and its source tarball
  about 1 MB smaller (#2937). It leaves out inputs that only the Python suites
  or no suite read, including four of its five copies of the Python packaging
  lock. Each third-party SAS test file now has its license beside it.
- `R/yamaa/DESCRIPTION` states the Rust its build uses: Rust 1.99.1, which
  rustup selects from the bundled `rust-toolchain.toml`, or Rust 1.90.0 or
  later without rustup. That file no longer lists Clippy or rustfmt, so a
  source installation under rustup no longer adds them.
- Native qualification installs the Linux-built Python and R source archives,
  the ones a release publishes, on macOS and Windows as well, instead of
  archives built on each host.

## Supported platforms and dependencies

- CPython 3.15 joins the supported interpreters, with wheels and source builds
  on Linux x86_64, macOS arm64 and Windows x64. The supported range is CPython
  3.12 through 3.15.
- On CPython 3.15, four Python dependency floors move to the oldest releases
  that work there: Polars 2.0.0, PyArrow 26.0.0, lxml 6.1.2 and Pydantic
  2.14.0 (#2871). CPython 3.12 to 3.14 keep Polars 1.35.2, PyArrow 23.0.1,
  lxml 6.1.0 and Pydantic 2.12.4.
- Release builds use Rust 1.99.1. The minimum supported Rust stays 1.90, and
  CI now checks and lints the workspace with Rust 1.90.0.

## Language

### Validation findings for shapes that failed as internal errors

0.4.0 refused the specifications below too, but only with an internal error
(`engine_rejected`) that named no cause. They now fail validation with a
finding that names the specification location and the rule (#2889):

- In a specification with row templates, a column computed after row
  construction that reads a key declared after it fails as
  `forward_reference` (REQ-0071), like a read of any other later column. A
  key that every row template derives itself is complete before that
  phase and may still be read.
- A named intermediate whose `key` list names one column twice fails as
  `invalid_field_type` (REQ-0115) at the repeated entry.
- A window whose `group_by` names one variable twice fails as
  `invalid_field_type` (REQ-0293) at the repeated entry.
