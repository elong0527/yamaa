# yamaa 0.5.0

yamaa 0.5.0 is not published (#3030 D1); the next published release is a
1.0.0 release candidate. These notes become the 1.0.0 notes, and the file is
renamed when the shared version moves to 1.0.0. #3050 plans the current
milestone and #3030 plans 1.0.0. The notes grow with each merged change, and
each change that breaks a user-facing interface gets a one-line entry, with no
step-by-step migration text.

## Install

0.5.0 is not distributed. #3030 D14 records how 1.0.0 is distributed.

The Linux wheel is `manylinux_2_34` and needs glibc 2.34 or later, for example
RHEL 9, Ubuntu 22.04 or Debian 12; older systems build from
`yamaa-0.5.0.tar.gz`.

### Source packages

- The installed R package carries only the test inputs that its installed
  suites read, so it is about 5 MB smaller on Linux and its source tarball
  about 1 MB smaller (#2937). It leaves out inputs that only the Python suites
  or no suite read, including four of its five copies of the Python packaging
  lock. Each third-party SAS test file now has its license beside it.
- `R/yamaa/DESCRIPTION` states the Rust its build uses: Rust 1.99.1, which
  rustup selects from the bundled `rust-toolchain.toml`, or Rust 1.90.0 or
  later without rustup. That file no longer lists Clippy or rustfmt, so a
  source installation under rustup no longer adds them.
- Native qualification installs the Linux-built Python and R source archives,
  the ones a release publishes, on macOS and Windows as well, instead of
  archives built on each host.

### License notices

- `LICENSE-THIRD-PARTY.txt` also carries the notices of the Rust standard
  library that the native extension links (#3009). It reproduces the notice
  that Rust 1.99.1 ships as `share/doc/rust/COPYRIGHT-library.html`: the
  licenses and copyright holders of the standard library's own files, with
  their license texts, and each out-of-tree crate with its notice texts. The
  Python License-Expression does not change.
- The `alloc-stdlib` entry names Dropbox's BSD-3-Clause license, which its
  repository ships in `alloc-no-stdlib`. It no longer names the canonical text
  with its placeholders unfilled.

## Supported platforms and dependencies

- CPython 3.15 joins the supported interpreters, with wheels and source builds
  on Linux x86_64, macOS arm64 and Windows x64. The supported range is CPython
  3.12 through 3.15.
- On CPython 3.15, three Python dependency floors move to the oldest releases
  that work there: Polars 2.0.0, PyArrow 26.0.0 and Pydantic 2.14.0 (#2871).
  CPython 3.12 to 3.14 keep Polars 1.35.2, PyArrow 23.0.1 and Pydantic 2.12.4.
- The lxml floor rises from 6.1.0 to 6.1.3 on every supported interpreter
  (#2943). lxml 6.1.3 stops loading external parameter entities by default,
  and 6.1.1 patched the libxslt that its Linux wheels bundle. yamaa's ODM
  reader was not exposed, and it no longer uses lxml: it moved into the Rust
  engine, which refuses a DOCTYPE, resolves only the five predefined entities
  and never reaches the network (#2967).
- Release builds use Rust 1.99.1. The minimum supported Rust stays 1.90, and
  CI now checks and lints the workspace with Rust 1.90.0.
- R no longer suggests nanoarrow: results are plain data.frames, so the
  nanoarrow 0.8.0 floor for Arrow views is gone (#2967).

## Language consolidation

0.5.0 carries the rules consolidation and language simplification that were
developed for a separate 1.0.0 line (#2855). The contracts are rewritten as
short rule cards under the principles that `rules/README.md` lists, and the
language keeps one way to state each thing. Most 0.4.0 specifications
need edits before they validate:

- **Some results move without an error.** A missing value sorts lowest, so it
  comes first in an ascending order unless the order term declares `nulls`.
  One rounding, the SAS-compatible near-tie rule, serves the rounding
  operation and CSV display precision, and `int` and `float` compare exactly.
  An imputation bound outside the collected month or year is ignored.
- **Many 0.4.0 spellings fail validation, each with a named condition:**
  `parents` (a specification has one `parent`), the retired `define.yaml`
  route, the `date_*` and `datetime_*` verbs (now `diff`, `shift`, `impute`
  and `precision` with a declared `type`), `previous_non_missing` (now
  `locf`), `str_concat` (now `str_template`), and a declaration that repeats
  another, such as `allowed_values` beside a bound codelist or a `unique`
  check on the keys.
- **One expression grammar** serves predicates, `compute` and `aggregate`,
  and every expression has one declared result type. Regular expressions use
  a portable subset without lookaround or backreferences, matched in linear
  time.
- **Declared metadata is enforced when a specification runs.** A mandatory
  column holds no missing value, and a bound codelist that lists its items
  limits the column's values even when the list is extensible.
- **A missing single input or an absent record gives missing by default,**
  counted like a declared handler; `require_match: true` states where a
  missing match must stop the run.
- **Every lookup runs one model of four steps** (LOOKUP-25): an implicit
  join, a named intermediate and a qualified aggregate match their keys and
  range, narrow the matched records by their filter, select one record or
  reduce them, and answer absence. A filter is asked only about records whose
  keys match, so a filter that would fail on a record no row matches no
  longer stops the run. A named intermediate that verifies a unique
  combination, or drives a row template, still asks its filter about every
  record, since it reads every record the filter keeps. A key value whose
  type cannot compare with its match value fails as `incompatible_input_type`
  for every kind, even on a record the filter would remove: an implicit join
  or an aggregate matched nothing before, and a named intermediate's filter
  hid the record, so a run that succeeded can now fail. In the order the
  model fixes, an aggregate evaluates its range value with its match values
  before any record is matched, even for a row whose missing key value
  matches nothing: a named intermediate that the range value reads is
  selected for that row too, its missing record counted at the aggregate's
  `between`, or failing the run when the intermediate declares
  `require_match`. A structured `source:` binding takes `between`, as a named
  intermediate and an aggregate do. On a row that a named intermediate
  drives, a range value qualified by the intermediate reads the record that
  built the row; a field the intermediate derives is not supported there yet
  and fails as `unsupported_operation`. An aggregate's empty `key` fails as
  `invalid_field_type`, as a named intermediate's does.
- **An input `schema` link types a stored artifact only.** A specification
  never runs its producing specification: build and save producers first, or
  let a project run order the builds of the specifications it lists. Its
  `output.path` and `output.report` may not name a file of a producer it
  links (`artifact_path_collision`).
- **A submission section's `datasets` chooses its transport files**, `xpt`
  for SAS XPORT version 5 or `json` for Dataset-JSON, written beside
  `define.xml`. Text lengths come from the data, ADaM dates are SAS numeric
  dates, and the Submission context enforces 40-character labels, 200-byte
  values and ASCII text.
- **Value-level metadata belongs to the column.** A column's
  `submission.value_level` entries describe the rows that a `where` clause
  over declared `str` output columns selects, so an ADaM parameter by
  `PARAMCD` or a supplemental qualifier by `QNAM` gets its own Define-XML
  definition, not only a `--TESTCD`. An entry's `mandatory`, codelist,
  length and date or time `data_type` are checked on those rows alone. A row
  template no longer declares `submission`. A row two entries select fails
  the run, and an entry that selects no row is a warning in the run report.

## Language

### Validation findings for shapes that failed as internal errors

0.4.0 refused the specifications below too, but only with an internal error
(`engine_rejected`) that named no cause. They now fail validation with a
finding that names the specification location and the rule (#2889):

- In a specification with row templates, a column computed after row
  construction that reads a key declared after it fails as
  `forward_reference` (REQ-0071), like a read of any other later column. A
  key that every row template derives itself is complete before that
  phase and may still be read.
- A named intermediate whose `key` list names one column twice fails as
  `invalid_field_type` (LOOKUP-5) at the repeated entry.
- A window whose `group_by` names one variable twice fails as
  `invalid_field_type` (REQ-0293) at the repeated entry.
- A named intermediate that declares `keep` beside an `order_by` listing no
  term fails as `unpaired_fields` (LOOKUP-10), with `order_by` reported
  missing, as a source's `keep` already does.
- A row template derivation that reads a column the template leaves to the
  column phase, through a formula, flag, rounding, window or `case`
  condition, fails as `phase_boundary` (REQ-0069) at that operand, naming
  the column and the row template, as a direct read of the column already
  did.
- A window that partitions, orders or reads by a driver field outside the
  groups fails as `ungrouped_driver_field`: in a grouped row template when
  the field is not one of its group keys (REQ-0067), and at column level
  when a grouped row template over that driver does not group by it
  (REQ-0107); one over a grouped row template with another driver fails as
  `unknown_field` (WINDOW-11).
- In the first row template, a read of a named intermediate whose `between`
  value reads a `SELF` intermediate, directly or through the `between`
  values of further intermediates, fails as `phase_boundary` (REQ-0120), as
  a direct read of the `SELF` intermediate already did. The finding names
  the read and then each `between` value it passes through.
- A named intermediate is checked in every context that reads it: each row
  template's derivations and row `filter`, and the rows of every template
  that a column derivation or a dataset verification reads it for. A match
  value, `between` value, correlated `filter` field or derivation that reads
  the record of an input that does not build the reading row fails as
  `unknown_field` (LOOKUP-5, LOOKUP-9, REQ-0120 or REQ-1185). In a grouped
  row template, a match value, `between` value or derivation that reads a
  driver field outside the group keys fails as `ungrouped_driver_field`
  (REQ-0067), naming the field, the intermediate, the row template and its
  driver. A read that several row templates make the same way is reported
  once, not once per template.
- A row template that reads a named intermediate whose `between` value is a
  column only the column phase completes, such as a window, fails as
  `phase_boundary` (LOOKUP-2) at that read, in a derivation or the row
  `filter`, naming the column, the intermediate and the row template. So does
  a read whose `between` value reads another intermediate that matches on
  such a column.

### Keys and record reads without row templates

A specification without row templates builds its rows from the distinct key
combinations of the base records (ROW-8). 0.4.0 stopped the shapes below with
an internal error (`engine_rejected`) that named no cause; they now build
(#2889):

- When a key is derived by a window, such as a `row_number` sequence, each
  base record is its own row, and every column reads that record. A flag,
  also inside a `case` branch, a `first_available` source and a project
  function argument read the record's field, and an `odm` read takes its
  scope from the record's own item group occurrence (NAME-10), as in a
  record-driven row template. An `odm` read inside a `case` branch builds
  in either kind of specification without row templates.
- A key may read a named intermediate's selection for its base record
  through a flag, a formula or a `case` condition, as a direct read of the
  intermediate already could, and a key may be a project function of the
  record's fields.

A key computed by an aggregate or an `odm` read, which read the records of a
key combination before any exists, now fails as `key_dependency` (COLUMN-7)
at that operation, naming the key column and the operation. COLUMN-7 now
states that a key is computed from one base record. With a window key, a key
is derived for its record's row as any column is, and both build.

### Column-level derivations on rows a named intermediate drives

0.4.0 listed this as a known issue: when every row template that completes
a column from its column-level derivation was driven by the same named
intermediate, `domain` stopped with `engine_rejected` (code
`result_projection`), and `check` reported nothing. The column now completes
those rows (#2930). The derivation reads them as the template would: the
intermediate's qualifier reads the record that built the row (REQ-0111),
another input joins on the output keys it carries, and a named lookup
matches through its key. A qualified aggregate still reduces its declared
input (REQ-0467).

Three reads of the intermediate are not supported there yet: a field it
derives, any field when it reads an input other than the one behind the
first row template's driver, and any field read beside an aggregate in the
same derivation. They fail before any data is read as
`unsupported_operation` at the derivation, in `check()` and in `run()`
alike. Read such a field inside the template instead, into its own column
when a column-level derivation needs it. Inside an aggregate's own
expression the intermediate is not an input the aggregate can reduce, so a
read there fails as `unknown_field` (REQ-0467).

### SAS datasets updated in place

A `.sas7bdat` input that still holds records deleted in place, for example
after `PROC SQL DELETE` or a DATA step `MODIFY` with `REMOVE`, now yields only
its live records, as SAS reads it (#2927). 0.4.0 refused it as
`source_sas_invalid` with cause `deleted_records`. The reader skips each
record marked in its page's deleted-record bitmap or by its compressed row's
deletion code, and checks that the records marked deleted are exactly the ones
the dataset counts. When they disagree it still fails with cause
`deleted_records` and the hint to rewrite the dataset first (SAS-8).

A compressed `.sas7bdat` input in which SAS moved an updated record to
another page is read too, with the moved record at its original position.
0.4.0 refused it with cause `compression`.

### Other SAS dataset reading fixes

The vendored ReadStat SAS readers take the upstream fixes since 1.1.9 that
apply to them (#2927):

- A compressed 64-bit dataset whose uncompressed record begins with the bytes
  of a subheader signature, such as a first value of 0.9999999999999999, is
  read. 0.4.0 failed it as malformed.
- A crafted dataset whose first records sit in a mix page and whose later
  records are RLE-compressed no longer crashes the host process.
- A zero-width character column, a SAS 7 release, the `J` and `TK` release
  tags and the alternative magic number are accepted.
- A dataset with no records reads column metadata from every page.

### SAS Transport version 8 observation counts

A version 8 `.xpt` input whose `OBSV8` header counts its observations now
yields exactly that many records (#2927). Trailing records made entirely of
blanks, such as rows whose every character field is empty, are data, where
0.4.0 dropped them as possible padding. A file with fewer records than its
count, or with anything but blank padding after them, fails as
`source_sas_invalid` with cause `malformed`. Without a count, in version 5
files and with a zero count, a trailing blank record is still treated as
possible padding when it is narrower than one 80-byte record. One at least 80
bytes wide is now data, since padding is always shorter (SAS-7).

### Malformed SAS and transport files

0.4.0 failed a SAS transport file whose member header declares no variables
with an internal error, and read a negative count as a column limit. Both now
fail as `source_sas_invalid` with cause `header`, as a SAS file without
columns does. A malformed SAS file could also make the reader reserve memory
for a column wider than any column it reads; that reservation now follows the
validated columns alone (#2928).

### Parquet fields whose Arrow schema names a view or a dictionary

0.4.0 listed this as a known issue: a Parquet field failed as
`source_field_type_unsupported` when the file's embedded Arrow schema named
it `string_view` or a `dictionary`, although pyarrow and Polars read the
file. pyarrow writes such fields for string views and dictionary-encoded
columns, Polars for `Categorical` and `Enum` columns and for a frame passed
to pyarrow through the Arrow PyCapsule interface, and the R arrow package
for factors. The schema names a layout, not a type, so these fields now read
by their Parquet type, with the values pyarrow reads (#2940). A `BYTE_ARRAY`
field annotated `String` reads as `str` under `string_view` or a dictionary
of strings with any index type. A dictionary of `int64`, `double`, `date32`
or `timestamp[us]` values reads as `int`, `float`, `date` or `datetime`.
REQ-1031 and REQ-1032 now state this. Casting such columns to plain strings
before writing is no longer needed.

### Parquet files with more than 32,768 row groups

0.4.0 listed this as a known issue: a Parquet file with more than 32,768 row
groups failed as `source_parquet_invalid`, although pyarrow and Polars read it.
pyarrow writes such files with a small `row_group_size` or when
`ParquetWriter.write_table` is called for each small batch, and Polars with a
small `row_group_size`. The Parquet decoder that yamaa pins reads at most
32,768 row groups from one footer. yamaa now presents a longer row-group list
to it in slices of at most 32,768 and joins the row groups in file order
(#2940), so every record reads in its stored order, with the values pyarrow
reads (REQ-1037). Files with at most 32,768 row groups read as before.

### DuckDB integer columns and int32 fields

0.4.0 listed this as a known issue: every DuckDB integer column failed as
`source_field_type_unsupported`. An `INT32` or `INT64` field now reads as
`int` when it has a signed integer annotation whose width fits its physical
type: the logical type `Int(bitWidth, signed)` or the matching converted type
`INT_8`, `INT_16`, `INT_32` or `INT_64` (#2940). An `INT32` field with no
annotation now reads as `int` too, as an `INT64` field with none already did.
DuckDB writes `BIGINT`, `INTEGER`, `SMALLINT` and `TINYINT` with the converted
type alone. pyarrow and Polars write `int8` and `int16` columns with both
annotations, and `int32` columns with none; 0.4.0 refused those too. All of
these now read with their stored values. Unsigned annotations stay refused. A
stored value outside the width its annotation declares fails as
`source_parquet_invalid`. REQ-1032 and REQ-1033 now state this.

### Parquet footers that admission refuses

Admission checks a Parquet footer before the Parquet decoder reads it. It now
also makes sure that the decoder reads only the values admission checked, and
that the decoder reserves no more memory for a list than a file within the
engine's limits needs (#3043). Each of the following fails as
`source_parquet_invalid`, except where a limit is named:

- A field that the decoder reads, written twice in one structure of the
  footer or of a page header. Writers never repeat a field, and the decoder
  does not always keep the copy that admission checked.
- More than 1,024 key-value metadata entries. This limit is new: the format
  sets none, writers write a few entries, and the engine reads one.
- Column orders other than one per leaf column, more sorting columns in a row
  group than the file has leaf columns, more than 36 encoding statistics in a
  column chunk (one per page type and encoding), or a level histogram longer
  than the 128 levels that a column can have.
- More row groups than the 10,000,000-row limit, which fails as that limit
  (`table_rows`). A row group that holds no rows counts too.
- An empty group in the schema now counts toward the 1,024-column limit
  (`columns`), as a leaf column does.

### Grouping findings name the grouped row template's own driver

The `dataset` context of an `ungrouped_driver_field` finding now names the
driver that the read names, which is the driver of the grouped row template
whose groups lack the variable (#3001). It used to name the input behind the
first row template. That was wrong when a later row template is over another
input, and for a row template driven by a named intermediate it named the
intermediate's input instead of the intermediate. The refusal, its
requirement and its paths are unchanged.

### Column-level driver reads check only that driver's grouped templates

A column-level derivation that reads a field of a row template's driver now
fails as `ungrouped_driver_field` (REQ-0107) only when a grouped row template
over that same driver does not group by the field (#3020). A grouped row
template over another input or named intermediate used to refuse the read
too, although its groups hold another driver's records. A column-level
window instead needs every row template to have the driver it reads
(WINDOW-11).

### Column-level lookups read the driver of the templates that leave the column

A column-level derivation evaluates only for the rows of the row templates
that leave the column to the column phase, so a lookup it reads now needs to
name only their driver (#3037). A range value, and a named intermediate's
key, range or correlated filter, may read the record of that driver
(LOOKUP-5, LOOKUP-8, LOOKUP-9). A row template that derives the column itself
used to refuse the read as well, as `unknown_field`, although its rows never
evaluate the column's derivation. A row template over another driver that
leaves the column to the column phase still refuses it.

### `check` reports every range value of an input that drives no reading row

A `between.value` qualified by an input that does not drive every row reading
the lookup still fails as `unknown_field` (LOOKUP-9) before any data is read.
`check()` now reports it wherever `run()` does, from the declarations alone
(#2951), where 0.4.0's `check()` reported it only at a qualified aggregate:

- at a named intermediate's range, however a row reaches the intermediate:
  through a derivation, a row template's `filter` or a dataset verification,
  from an aggregate's `derive` binding, or through the range value of another
  intermediate, an aggregate or a structured `source:` binding;
- at a structured `source:` binding's own range, also as a source of
  `first_available`, `mapping` or `cut`;
- at an aggregate's range inside a `case` result.

### Collected dates and times

A CDISC review of the date handling added these checks and operations
(#2855):

- **Declared date and time types are checked.** A `str` column whose
  submission `data_type` is a date or time type, such as `date`,
  `partialDatetime` or `intervalDatetime`, has each present value checked
  against that type's ISO 8601 form (SUB-26). A value-level entry's own
  `data_type` decides the rows its `where` clause selects. A value of another
  form fails as `data_type_failed`, and the run report names the check
  `data_type`.
  `datetime` means complete to the second, so text collected to the minute is
  a `partialDatetime`.
- **A tabulation dataset has no `datetime` output column.** In an `sdtm` or
  `send` dataset such a column fails validation with `value_not_permitted`
  (SUB-27), because its text writes seconds that were never collected. An
  internal `datetime` column is still allowed.
- **`dtc` and `time_of_day`.** `dtc` writes collected `year` to `second` parts
  as ISO 8601 text that stops before the first missing part, so a day
  collected without its month keeps the year alone (TIME-19). `time_of_day`
  returns a datetime's whole seconds since midnight, the ADaM `*TM` value,
  which an `int` column shows with `TIME8.` (TIME-20).
- **SDTM text with an unknown component is read by its prefix.** `precision`,
  `impute` and `to_date` read `2025---15` as `2025` and `2025-03-15T-:30` as
  `2025-03-15`, text that 0.4.0 refused as invalid (TIME-7). An ISO 8601 interval
  or duration, such as `2025-01-01/2025-01-10` or `P3D`, fails as the new
  `interval_or_duration_text` instead of `invalid_date_text`, and the same
  `invalid` handler answers both (TIME-13).

## Python and R

### Public API

Python and R share one API of spec and project objects, with the same
operations in both hosts (#2967). The Python package exports `spec`,
`project`, `read_odm`, `Error` and `__version__`. The R package exports
`yamaa_spec`, `yamaa_project` and `yamaa_read_odm`, and signals failures as
`yamaa_error` conditions. `spec(path)` opens one specification and
`project(path)` a study's project file. Neither reads anything until a method
runs, and every method rereads the files:

| Call | Returns |
| --- | --- |
| `spec.check()` | Static findings in `issues`, without reading study data. |
| `spec.resolve()` | The composed specification as a dict or named list. |
| `spec.run()` | A run: `output`, `issues`, `report` and `save()`. |
| `project.spec(name)` | The listed specification whose `domain` is `name`, with the project's codelists and functions. |
| `project.check()` | Static findings for every listed specification and the project. |
| `project.run(section)` | A project run of one section or all: `names`, one read-only run per specification (`runs["ADSL"]`, `runs[["ADSL"]]` in R), `issues`, `report` and `save()`. |
| `project.submission(section, created=)` | define.xml, and the Dataset-JSON or SAS Transport files a section's `datasets` asks for: `issues` and `save()`. |

Results publish nothing until `save()`, which writes exactly what was built.
`check()` and `run()` return problems as issues rather than raising;
`save()`, `resolve()` and an unknown specification name or section raise
`yamaa.Error` in Python or a `yamaa_error` condition in R, carrying `issues`.
Python returns Polars DataFrames, and integers keep separate missingness in
both hosts and the full signed 64-bit range in Python. R returns data.frames
of plain double and character columns and passes project functions plain
values the same way; an integer beyond 2^53 or text containing NUL raises an
error instead of changing. R gains `yamaa_read_odm()`, so converting ODM no
longer needs Python (#2933). The R and Python API page,
`docs/articles/api.md`, shows every call in both languages.

### Repeated runs reuse their compilation

A spec or project object compiles on its first `run()` and keeps what it
compiled (#2821). A later `run()` of the same object first checks that every
file the specification was compiled from is unchanged: the specification and
its layers, dictionaries and linked producers, the project file, the
environment file, and the lock, function definitions and codelists they
declare. When they are, the run reuses the compilation; when one changed or is
gone, the run compiles again, so it never uses stale files. A project object
keeps one compilation per specification its runs built. Every `run()` still
reads its input data and activates the project functions afresh, so results
are the same as compiling each time. No call or result changes.

### One issues table

Every finding is one row of the `issues` table, built in Rust and identical in
both hosts: `phase`, `condition`, `requirement`, `spec_paths`, `context` as
canonical JSON text, then `source_span`, the start and end byte offsets into
the failing expression, and `operand_route`, the operand steps from the
expression root to the failing node. Both are missing when the failure
recorded no place in an expression. The error a failed call raises carries the
same table. The separate `diagnostics` records are gone.

### One run report

One run report replaces the verification and warning logs (#2912).
`output.report` replaces `output.verification_log` and `output.warning_log`,
and a run's `report` replaces its `verification_log` and `warning_log`. The
report has fourteen columns: one row for the run, then one per input, row
template, handler, output column and evaluated check. Every run that began
has one in memory; `save()` writes it to `output.report` before the dataset,
and a failed run's `save()` writes only the report. A violated warning does not
fail the run (REQ-0390), so it appears in the report (REQ-0393) and not in
`issues`.

The `handler` rows list every handler path, registered before any row is read,
so a path that answers nothing has a row with `COUNT` 0 (COLUMN-14, #2938). Two
groups of paths used to be missing until they fired, or for good:

- a named intermediate read's `no_match`, unless the intermediate declares
  `require_match: true`, and its `multiple_matches` when the intermediate
  declares `keep`. Both appeared only after their first answer, in the order
  they fired;
- the paths inside an intermediate's `derivations:`, of which only a typed
  derivation's `unconvertible` was reported.

A path inside intermediate derivations counts every donor record it answers,
each time the donor records are built. A derivation that reads the current
input record builds them once per current record, so its counts grow with the
rows that read the intermediate.

The rows now follow one documented order (COLUMN-14). First come the
`unconvertible` paths, then each derivation in evaluation order with its
paths in expression order, then the intermediates' key expressions, then the
paths inside intermediate derivations. Within one source binding,
`multiple_matches` now comes before `absent`.

### Project files

A `project.yaml` lists a study's specifications by section, with the metadata
they share (#2967). Its `environments` names each language's environment file,
and `codelists`, `study` and the `sdtm`, `adam` and `send` sections move there
from the environment file. An environment file keeps `schema_version`, `lock`
and `functions`; the `environments` key states its language, so environment
files no longer declare `language`. A section needs only `specs` to run;
`study`, `standard` and `define` are required only to create submission
files. `datasets: json` replaces `dataset_json: true`, and `datasets: xpt`
writes SAS Transport version 5 files instead. A listed specification's name is
its `domain`, unique across the project (REQ-1331 to REQ-1348).

A project run builds each listed specification of the selected sections once,
in dependency order, and hands a producer's result in memory to the
specifications that link it through `schema`. A linked producer outside the
run is read from its saved file, so ADaM can be rerun against finished SDTM. A
failed specification stops only the specifications that read it. Saving checks
every target first and writes no dataset unless every specification succeeded.

Pass the project file explicitly; it is not discovered. Relative paths in the
project file resolve from the project file, and those in an environment file
from that file. An output's `relative_to: entry` also covers the run report.

## Rust

- `Engine::compile` prepares a specification once and returns an owned,
  reusable `Plan`; `Plan::run` runs it, as often as needed, each time as an
  independent attempt with its own inputs (#2821). Compilation reads no study
  data. A `RunRequest` can give one run its own resolver, for the inputs and
  the Save targets, and its own progress observer. A `Plan` is `Send`,
  `Sync` and cheap to clone, and a `Build` outlives the plan that ran it.
- `Engine::build` is now exactly one `compile` followed by one `run`, with
  the same results and events as before.
- A refused compilation returns a `Plan` whose `report` holds the
  diagnostics; each of its runs returns that failed build without reading
  anything.
- A plan never runs stale. Each run first checks that every file it was
  compiled from is unchanged (the specification and its layers,
  dictionaries and linked producers, the project file, the environment file,
  the lock, function definitions and codelists), and activates the project
  functions afresh. A changed file refuses that run with
  `resource_path_content_changed`, naming the field that declared it.
  Nothing recompiles on its own: the plan runs again once the original is
  back, and a new `compile` picks up the change.
- The operations behind the Python and R packages are `Engine` methods too:
  `spec_check`, `spec_run`, `spec_resolve`, `project_spec`, `project_check`,
  `project_run` and `project_submission`, with `odm::read_odm` for ODM XML
  (#2967).
- `Plans` holds the plans a host object compiled, one per specification
  (#2821). `Engine::spec_run_reusing` and `Engine::project_run_reusing` run
  through one: a kept plan runs again when the run-start check finds its files
  unchanged, and the specification compiles again when one changed.
  `spec_run` and `project_run` run through an empty holder.
- The facade forwards a fourth independent feature, `odm`, on by default
  beside `yaml`, `parquet` and `readstat`. `default-features = false,
  features = ["yaml", "parquet"]` also omits the ODM XML reader. The Python
  and R packages enable all four.
- Every native host export names its counterpart in the other host unless the
  binding definition declares it host transport.
- A panic that the Parquet or Arrow crate raises on a malformed Parquet
  source is still one `source_parquet_invalid` finding, and no longer prints
  to stderr in Python, R or an embedder (#2941, #3043). The engine's first
  native decode wraps the process's panic hook, once. The wrapper prints
  nothing for a panic inside the engine's calls into those crates to decode
  Parquet, the file's embedded Arrow schema included. It passes every other
  panic to the hook it wraps, such as one in Arrow's import of a host table,
  or a further panic on the same thread while a contained one unwinds, after
  which the process aborts with that message. Only the calls into those
  crates are contained: a panic in yamaa's own code around them is a bug, and
  no longer reads as an invalid source.
- Stable Rust installs a panic hook in two steps, so while the wrapper is
  installed, a panic on another thread goes to Rust's default hook, and a
  hook that another thread sets is replaced. An embedder with its own hook
  should set it before the engine's first Parquet read. A hook set later
  replaces the wrapper and runs for every panic, contained ones included;
  when it calls the hook it replaced, only that call stays silent.

### Embedders get the reviewed YAML parser

A project that depends on the `yamaa` facade by git or path now builds the
reviewed YAML parser with no other configuration (#2929). In 0.4.0 the parser
reached the engine through a `[patch]` in yamaa's own workspace, which Cargo
applies only when that workspace is the root. Such a project built the
published `saphyr-parser` 0.2.2 instead and refused valid specifications that
the Python and R packages accept, such as a block-style file containing
`verifications: [row_count: {min: 3, max: 3}]`. `yamaa-adapters` now depends
on the vendored copy by path, under its own crate name `yamaa-saphyr-parser`,
so a graph that already holds a published `saphyr-parser` keeps both crates
without a name collision. A `[patch.crates-io]` entry for `saphyr-parser`
added to work around this is now unused and can be removed.

## Migration

### From 0.4.0

Each change that breaks a user-facing interface adds its one-line entry here,
as AGENTS.md requires.

Each 0.4.0 Python call has one replacement (#2967). R makes the same calls
through `yamaa_spec()`, `yamaa_project()` and `yamaa_read_odm()`:

| 0.4.0 | 0.5.0 |
| --- | --- |
| `yamaa.domain("dm.yaml", environment="python/environment.yaml")` | `yamaa.project("project.yaml").spec("DM").run()` |
| `yamaa.domain("dm.yaml")` | `yamaa.spec("dm.yaml").run()` |
| `yamaa.check("dm.yaml", environment=...)` | `yamaa.project("project.yaml").spec("DM").check()`, or `yamaa.spec("dm.yaml").check()` |
| `yamaa.define("environment.yaml", "sdtm", created=t)` | `yamaa.project("project.yaml").submission("sdtm", created=t)` |
| `yamaa.resolve_specification(...)` | `yamaa.spec(path).resolve()` |
| A loop over every SDTM or ADaM specification | `yamaa.project("project.yaml").run("sdtm")` or `.run("adam")` |
| `result.verification_log`, `result.warning_log` | `run.report` |
| `output_arrow` and the other Arrow views | `run.output` and `run.report`, as DataFrames |
| `result.save()`, which returns `True` | `run.save()`, which returns nothing and raises `yamaa.Error` |
| `DomainError`, `DefineError`, `ResolvedSpecificationError` | `yamaa.Error`, carrying `issues` |
| `result.diagnostics`, `Diagnostic`, `SourceSpan` | The `issues` columns `context`, `source_span` and `operand_route` |
| `yamaa.write_odm_parquet(...)` | `yamaa.read_odm(...)`, then write the table as Parquet |
| `resolver=` and `yamaa.resources` | No replacement: inputs and environments are read from the paths the specification and project file name |

- **Project files.** Move `codelists`, `study` and the `sdtm`, `adam` and
  `send` sections from the environment file into one `project.yaml`, name each
  language's environment file under its `environments`, and delete `language`
  from the environment files. Replace `dataset_json: true` with
  `datasets: json`, or with `datasets: xpt` for SAS Transport version 5
  files.
- **Run reports.** Replace `output.verification_log` and `output.warning_log`
  with one `output.report`, whose fourteen columns replace the columns of both
  logs.
- **Value-level metadata.** Move each row template's `submission` map into
  its column's `submission` as one `value_level` entry per test code, with an
  `id` and a `where` clause, such as
  `{id: GLUC, where: {LBTESTCD: [GLUC]}, codelist: CL_GLUCOSE}`. Per-value
  Define-XML identifiers end in the entry `id`, so an `id` equal to the test
  code keeps them. Issues of value-level checks are reported at
  `columns.<column>.submission.value_level.<id>`, with `entry` in their
  context instead of `testcd`. `value_metadata_requires_testcd`,
  `value_metadata_requires_literal_testcd`, `value_metadata_unknown_column`,
  `value_metadata_not_output_column` and `conflicting_value_metadata` are
  gone: a where clause that cannot select rows fails as
  `value_level_where_invalid`, and two entries that can select one row as
  `value_level_overlap`. A where column must be a `str` column, whatever
  metadata the entry declares: 0.4.0 accepted value-level metadata over a
  `<DOMAIN>TESTCD` declared `int`, or another type that is not `str`, unless
  a per-value check selected rows by the code, and such an entry now fails as
  `value_level_where_invalid` with `reason: not_str` (SUB-12). Declare the
  test code `str`, even when its codes are digits.
- **R values.** R results and project function arguments are plain doubles
  and character vectors. The `yamaa_int64_vector` and `yamaa_utf8_vector`
  classes are gone; an integer beyond 2^53 or text containing NUL raises an
  error instead.
- **Issues.** The `issues` table keeps its five columns and adds
  `source_span` and `operand_route`; `context` stays canonical JSON text.
- **Conditions.** `missing_warning_log` is now `missing_report`.
  `runner_language_mismatch` is gone, because environment files no longer
  declare a language. `missing_aggregate_keys` is gone: an aggregate's empty
  `key` fails as `invalid_field_type` (LOOKUP-5), reporting `expected` where
  0.4.0 reported the empty `key`. An aggregate's `between` without a bound
  fails as `invalid_field_type` (LOOKUP-9), reporting `expected`, where 0.4.0
  reported `invalid_aggregate_context` (REQ-0329) with `expr` and `reason` at
  the same path. Code that matches on any of these names must change.
- **Lookup requirements.** The lookup findings below keep their condition
  and paths and now cite the rule card that owns them, so code that matches
  on `requirement` must change:
  - `unmatched_key` of a named intermediate: REQ-0124 becomes LOOKUP-24;
  - `unpaired_fields`: REQ-0119 becomes LOOKUP-10;
  - `invalid_field_type` of a named intermediate's empty `key`: REQ-0115
    becomes LOOKUP-5;
  - `no_applicable_keys`: REQ-0152 and REQ-0153 become LOOKUP-5;
  - `unknown_field` of a `key` column or a match value: REQ-0116, REQ-0117
    and REQ-0141 become LOOKUP-5;
  - `incompatible_input_type` of a key pair: REQ-0004, REQ-0151 and
    REQ-0323 become LOOKUP-9;
  - `invalid_field_type` of a named intermediate's `between` without a bound:
    REQ-1049 becomes LOOKUP-9;
  - `unknown_field` and `incomparable_range_types` of a `between` value or
    bound: REQ-0121 becomes LOOKUP-9.
- **Lookup contexts.** The `no_applicable_keys` hint of an implicit join is
  now "declare a named intermediate with its `key`", and of an aggregate
  "declare the `key` explicitly", the hint a named intermediate already gave;
  0.4.0 told both to declare an explicit `intermediate:` with `source`/`key`
  pairs. The `incompatible_input_type` finding of a named intermediate's
  inferred key now names the `intermediate`.
- **Grouped row counts.** A grouped `row_count` names every offending group's
  count as `counts`, and `denominators` with a fraction bound, even when one
  group offends. 0.4.0 used the single `count` and `denominator` for that
  case. An ungrouped `row_count` keeps `count` and `denominator`.
- **Column-level windows.** A column-level window that reads a field of a
  driver not every row template has fails as `unknown_field` (WINDOW-11); it
  used to build, reading another dataset's records (#3042).
- **R errors.** Every refusal is a `yamaa_error` condition carrying `issues`.
  It replaces `yamaa_domain_error`, `yamaa_define_error` and
  `yamaa_resolved_specification_error`. An argument mistake is an ordinary R
  error, no longer a `yamaa_argument_error`.
- **ODM tables.** `yamaa.read_odm()` returns `ValuePresent` and `IsNull` as the
  text `"true"` or `"false"`, no longer Booleans, and `SourceOrdinal` as a
  signed 64-bit integer, no longer an unsigned one. An input it refuses raises
  `yamaa.Error`, which is not a `ValueError`. Code that caught `ValueError`
  from the old `ODMError` must catch `yamaa.Error`. R gains
  `yamaa_read_odm()` with the same table.
- **Resolved specifications.** `spec.resolve()` returns plain data:
  `ResolvedSpecification`, its `to_json()`, `from_json()` and `to_dict()`,
  and R's `yamaa_read_resolved_specification()` are gone, so saved 0.4.0 JSON
  is not read back. In the returned facts, the `environment` key is now
  `project`, and the `warning_log` and `verification_log` resource roles are
  now one `report` role.
- **Collected dates.** A `str` column that declares `data_type: datetime`
  must hold date-times complete to the second: declare `partialDatetime`, or
  another partial or incomplete type, for text collected to the minute, the
  day or the month. An `sdtm` or `send` dataset carries its dates and times in
  `str` columns, never in a `datetime` output column. Code that matches
  `invalid_date_text` for an ISO 8601 interval or duration must match
  `interval_or_duration_text`.
- **First-template filters that read `SELF`.** 0.4.0 ran a first row
  template's `filter` that reads a `SELF` intermediate, directly or through
  `between` values, although no row is complete while the first template
  filters: the read always found no row, so a filter such as
  `RECORDED.VISIT IS NULL` kept every candidate. It now fails as
  `phase_boundary` (REQ-0120) at `rows[0].filter`, as a first-template
  derivation reading `SELF` already did. Build the rows the filter compares
  with in an earlier row template.
- **Lookup match values from the column phase.** A row template that reads a
  named intermediate whose `key` match value is a column only the column
  phase completes failed in 0.4.0 as `unknown_field` (REQ-0117) at the
  intermediate's `key`. It now fails as `phase_boundary` (LOOKUP-2) at the
  row template's read, naming the column, the intermediate and the row
  template, as a `between` value from the column phase does. Code that
  matches the old condition or path must change. To repair the
  specification, derive the column that reads the intermediate at column
  level, or derive the match value in the row template.

The [language consolidation](#language-consolidation) breaks most 0.4.0
specifications. Each refused spelling fails validation with a named condition
that points at its replacement. The complete step-by-step guide, drafted for
the 1.0.0 line in #2984, lands here before 0.5.0 is qualified.
