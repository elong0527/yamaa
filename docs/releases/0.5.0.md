# yamaa 0.5.0

yamaa 0.5.0 is in development on the `release/0.5.0` branch; the plan is
#2785. These notes grow with each merged change and are finished before the
release is qualified.

## Install

0.5.0 will be distributed the same way as 0.4.0, as assets of the GitHub
release tagged `yamaa-v0.5.0`, unless #2785 records a different decision.

The Linux wheel is `manylinux_2_34` and needs glibc 2.34 or later, for example
RHEL 9, Ubuntu 22.04 or Debian 12; older systems build from
`yamaa-0.5.0.tar.gz`.

## Supported platforms and dependencies

- CPython 3.15 joins the supported interpreters, with wheels and source builds
  on Linux x86_64, macOS arm64 and Windows x64. The supported range is CPython
  3.12 through 3.15.
- On CPython 3.15, three Python dependency floors move to the oldest releases
  that work there: Polars 2.0.0, PyArrow 26.0.0 and Pydantic 2.14.0 (#2871).
  CPython 3.12 to 3.14 keep Polars 1.35.2, PyArrow 23.0.1 and Pydantic 2.12.4.
- The lxml floor rises from 6.1.0 to 6.1.3 on every supported interpreter
  (#2943). lxml 6.1.3 stops loading external parameter entities by default,
  and 6.1.1 patched the libxslt that its Linux wheels bundle. yamaa's ODM
  reader was not exposed: it disables entity resolution, DTD loading and
  network access, and it never uses XSLT.
- Release builds use Rust 1.99.1. The minimum supported Rust stays 1.90, and
  CI now checks and lints the workspace with Rust 1.90.0.
- R no longer suggests nanoarrow: results are plain data.frames, so the
  nanoarrow 0.8.0 floor for Arrow views is gone (#2967).

## Language

### Validation findings for shapes that failed as internal errors

0.4.0 refused the specifications below too, but only with an internal error
(`engine_rejected`) that named no cause. They now fail validation with a
finding that names the specification location and the rule (#2889):

- In a specification with row templates, a column computed after row
  construction that reads a key declared after it fails as
  `forward_reference` (REQ-0071), like a read of any other later column. A
  key that every row template derives itself is complete before that
  phase and may still be read.
- A named intermediate whose `key` list names one column twice fails as
  `invalid_field_type` (REQ-0115) at the repeated entry.
- A window whose `group_by` names one variable twice fails as
  `invalid_field_type` (REQ-0293) at the repeated entry.
- Value-level metadata that checks only the rows of one test code, such as
  a per-value `length` that differs from the column's, over a
  `<DOMAIN>TESTCD` column not declared `str` fails as
  `value_metadata_requires_literal_testcd` (REQ-1164) at the row template's
  `submission`. Value-level metadata that checks no rows by test code, such
  as a per-value `origin`, is unchanged.
- A named intermediate that declares `keep` beside an `order_by` listing no
  term fails as `unpaired_fields` (REQ-0119), with `order_by` reported
  missing, as a source's `keep` already does.
- A row template derivation that reads a column the template leaves to the
  column phase, through a formula, flag, rounding, window or `case`
  condition, fails as `phase_boundary` (REQ-0069) at that operand, naming
  the column and the row template, as a direct read of the column already
  did.
- A window that partitions, orders or reads by a driver field outside the
  groups fails as `ungrouped_driver_field`: in a grouped row template when
  the field is not one of its group keys (REQ-0067), and at column level
  when a grouped row template does not group by it (REQ-0107).
- In the first row template, a read of a named intermediate whose `between`
  value reads a `SELF` intermediate, directly or through the `between`
  values of further intermediates, fails as `phase_boundary` (REQ-0120), as
  a direct read of the `SELF` intermediate already did. The finding names
  the read and then each `between` value it passes through.

### Column-level derivations on rows a named intermediate drives

0.4.0 listed this as a known issue: when every row template that completes
a column from its column-level derivation was driven by the same named
intermediate, `domain` stopped with `engine_rejected` (code
`result_projection`), and `check` reported nothing. The column now completes
those rows (#2930). The derivation reads them as the template would: the
intermediate's qualifier reads the record that built the row (REQ-0111),
another input joins on the output keys it carries, and a named lookup
matches through its key. A qualified aggregate still reduces its declared
input (REQ-0467).

Three reads of the intermediate are not supported there yet: a field it
derives, any field when it reads an input other than the one behind the
first row template's driver, and any field read beside an aggregate in the
same derivation. They fail before any data is read as
`unsupported_operation` at the derivation, in `check()` and in `run()`
alike. Read such a field inside the template instead, into its own column
when a column-level derivation needs it. Inside an aggregate's own
expression the intermediate is not an input the aggregate can reduce, so a
read there fails as `unknown_field` (REQ-0467).

## Python and R

### Public API

Python and R share one API of spec and project objects, with the same
operations in both hosts (#2967). The Python package exports `spec`,
`project`, `read_odm`, `Error` and `__version__`. The R package exports
`yamaa_spec`, `yamaa_project` and `yamaa_read_odm`, and signals failures as
`yamaa_error` conditions. `spec(path)` opens one specification and
`project(path)` a study's project file. Neither reads anything until a method
runs, and every method rereads the files:

| Call | Returns |
| --- | --- |
| `spec.check()` | Static findings in `issues`, without reading study data. |
| `spec.resolve()` | The composed specification as a dict or named list. |
| `spec.run()` | A run: `output`, `issues`, `report` and `save()`. |
| `project.spec(name)` | The listed specification whose `domain` is `name`, with the project's codelists and functions. |
| `project.check()` | Static findings for every listed specification and the project. |
| `project.run(section)` | A project run of one section or all: `names`, one read-only run per specification (`runs["ADSL"]`, `runs[["ADSL"]]` in R), `issues`, `report` and `save()`. |
| `project.submission(section, created=)` | define.xml, and Dataset-JSON where a section asks for it: `issues` and `save()`. |

Results publish nothing until `save()`, which writes exactly what was built.
`check()` and `run()` return problems as issues rather than raising;
`save()`, `resolve()` and an unknown specification name or section raise
`yamaa.Error` in Python or a `yamaa_error` condition in R, carrying `issues`.
Python returns Polars DataFrames, and integers keep separate missingness in
both hosts and the full signed 64-bit range in Python. R returns data.frames
of plain double and character columns and passes project functions plain
values the same way; an integer beyond 2^53 or text containing NUL raises an
error instead of changing. R gains `yamaa_read_odm()`, so converting ODM no
longer needs Python (#2933). The R and Python API page,
`docs/articles/api.md`, shows every call in both languages.

### One issues table

Every finding is one row of the `issues` table, built in Rust and identical in
both hosts: `phase`, `condition`, `requirement`, `spec_paths`, `context` as
canonical JSON text, then `source_span`, the start and end byte offsets into
the failing expression, and `operand_route`, the operand steps from the
expression root to the failing node. Both are missing when the failure
recorded no place in an expression. The error a failed call raises carries the
same table. The separate `diagnostics` records are gone.

### One run report

One run report replaces the verification and warning logs (#2912).
`output.report` replaces `output.verification_log` and `output.warning_log`,
and a run's `report` replaces its `verification_log` and `warning_log`. The
report has fourteen columns: one row for the run, then one per input, row
template, handler, output column and evaluated check. Every run that began
has one in memory; `save()` writes it to `output.report` before the dataset,
and a failed run's `save()` writes only the report. A violated warning appears
in the report and not in `issues` (REQ-0392).

### Project files

A `project.yaml` lists a study's specifications by section, with the metadata
they share (#2967). Its `environments` names each language's environment file,
and `codelists`, `study` and the `sdtm`, `adam` and `send` sections move there
from the environment file. An environment file keeps `schema_version`, `lock`
and `functions`; the `environments` key states its language, so environment
files no longer declare `language`. A section needs only `specs` to run;
`study`, `standard` and `define` are required only to create submission
files, and `datasets: json` replaces `dataset_json: true`. A listed
specification's name is its `domain`, unique across the project (REQ-1331 to
REQ-1348).

A project run builds each listed specification of the selected sections once,
in dependency order, and hands a producer's result in memory to the
specifications that link it through `schema`. A linked producer outside the
run is read from its saved file, so ADaM can be rerun against finished SDTM. A
failed specification stops only the specifications that read it. Saving checks
every target first and writes no dataset unless every specification succeeded.

Pass the project file explicitly; it is not discovered. Relative paths in the
project file resolve from the project file, and those in an environment file
from that file. An output's `relative_to: entry` also covers the run report.

## Rust

- `Engine::compile` prepares a specification once and returns an owned,
  reusable `Plan`; `Plan::run` runs it, as often as needed, each time as an
  independent attempt with its own inputs (#2821). Compilation reads no study
  data. A `RunRequest` can give one run its own resolver, for the inputs and
  the Save targets, and its own progress observer. A `Plan` is `Send`,
  `Sync` and cheap to clone, and a `Build` outlives the plan that ran it.
- `Engine::build` is now exactly one `compile` followed by one `run`, with
  the same results and events as before.
- A refused compilation returns a `Plan` whose `report` holds the
  diagnostics; each of its runs returns that failed build without reading
  anything.
- The operations behind the Python and R packages are `Engine` methods too:
  `spec_check`, `spec_run`, `spec_resolve`, `project_spec`, `project_check`,
  `project_run` and `project_submission`, with `odm::read_odm` for ODM XML
  (#2967).
- The facade forwards a fourth independent feature, `odm`, on by default
  beside `yaml`, `parquet` and `readstat`. `default-features = false,
  features = ["yaml", "parquet"]` also omits the ODM XML reader. The Python
  and R packages enable all four.
- Every native host export names its counterpart in the other host unless the
  binding definition declares it host transport.

## Migration

### From 0.4.0

Each change that breaks a user-facing interface adds its migration note here,
as AGENTS.md requires.

Each 0.4.0 Python call has one replacement (#2967). R makes the same calls
through `yamaa_spec()`, `yamaa_project()` and `yamaa_read_odm()`:

| 0.4.0 | 0.5.0 |
| --- | --- |
| `yamaa.domain("dm.yaml", environment="python/environment.yaml")` | `yamaa.project("project.yaml").spec("DM").run()` |
| `yamaa.domain("dm.yaml")` | `yamaa.spec("dm.yaml").run()` |
| `yamaa.check("dm.yaml", environment=...)` | `yamaa.project("project.yaml").spec("DM").check()`, or `yamaa.spec("dm.yaml").check()` |
| `yamaa.define("environment.yaml", "sdtm", created=t)` | `yamaa.project("project.yaml").submission("sdtm", created=t)` |
| `yamaa.resolve_specification(...)` | `yamaa.spec(path).resolve()` |
| A loop over every SDTM or ADaM specification | `yamaa.project("project.yaml").run("sdtm")` or `.run("adam")` |
| `result.verification_log`, `result.warning_log` | `run.report` |
| `output_arrow` and the other Arrow views | `run.output` and `run.report`, as DataFrames |
| `result.save()`, which returns `True` | `run.save()`, which returns nothing and raises `yamaa.Error` |
| `DomainError`, `DefineError`, `ResolvedSpecificationError` | `yamaa.Error`, carrying `issues` |
| `result.diagnostics`, `Diagnostic`, `SourceSpan` | The `issues` columns `context`, `source_span` and `operand_route` |
| `yamaa.write_odm_parquet(...)` | `yamaa.read_odm(...)`, then write the table as Parquet |
| `resolver=` and `yamaa.resources` | No replacement: inputs and environments are read from the paths the specification and project file name |

- **Project files.** Move `codelists`, `study` and the `sdtm`, `adam` and
  `send` sections from the environment file into one `project.yaml`, name each
  language's environment file under its `environments`, and delete `language`
  from the environment files. Replace `dataset_json: true` with
  `datasets: json`.
- **Run reports.** Replace `output.verification_log` and `output.warning_log`
  with one `output.report`, whose fourteen columns replace the columns of both
  logs.
- **R values.** R results and project function arguments are plain doubles
  and character vectors. The `yamaa_int64_vector` and `yamaa_utf8_vector`
  classes are gone; an integer beyond 2^53 or text containing NUL raises an
  error instead.
- **Issues.** The `issues` table keeps its five columns and adds
  `source_span` and `operand_route`; `context` stays canonical JSON text.
