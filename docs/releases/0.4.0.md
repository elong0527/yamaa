# yamaa 0.4.0

Python and R now use one shared Rust engine for specification admission,
execution, verification, Define documents and explicit Save. The Rust crates
remain private and are included in the standalone source packages.

The retained Python API is `domain`, `check`, `define`, their result/error APIs,
version metadata and `read_odm`/`write_odm_parquet`; R retains its corresponding
functions, including `yamaa_define`. Legacy Python evaluators, probes, resolved
specification and IO/authoring extensions, and `cdiscbuilder` are removed. Build
holds results without publishing; Save uses retained bytes. Integers preserve
the complete signed 64-bit range and missingness separately in both hosts.

Supported platforms are CPython 3.12-3.14 on Linux x86_64, macOS arm64 and Windows
x64, and R 4.6.1 source builds on those hosts. Each attached wheel is the exact
artifact tested on all supported interpreters for its OS. The attached Python
sdist and R tarball are the exact archives tested on Linux; native CI separately
qualifies source builds from each host's archive on macOS and Windows.

Download the wheel for your platform, then install it with
`python -m pip install ./yamaa-0.4.0-<wheel-tags>.whl`. For a Python source build,
use `python -m pip install ./yamaa-0.4.0.tar.gz`. For R, use
`install.packages("yamaa_0.4.0.tar.gz", repos = NULL, type = "source")`.
Source installation needs Rust 1.90.0/Cargo, a C compiler and GNU make; Windows R
also needs Rtools45 and the `x86_64-pc-windows-gnu` Rust target. R needs no Python
runtime. R is distributed through the GitHub source asset; CRAN, r-universe and
R binaries are later work. These GitHub assets do not establish PyPI publication.

Pass project `environment` files explicitly and use their current function
contracts and tests. A packaging `lock` is optional: without one, activation
still binds every called function and runs all its conformance cases, while
skipping package-version checks. A declared lock is required to exist and pass
verification; regenerate older project locks for 0.4.0. Metadata diagnostics
retain authored declaration paths and original failure facts.

Relative resources resolve from their declaring YAML file by default. An input
or output declaration may select `relative_to: entry` to share program layers
across studies while reading and saving beside each study's entry. For an
input, the selected base applies to both `path` and `schema`; each linked
producer uses its own entry. Output selection also applies to warning and
verification logs. Absolute paths retain their written destination. The
[release and migration guide](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md)
lists the language spelling changes and installation guides. These explicit
choices replace old project-root/data-root discovery; Save still publishes the
bytes retained by Build.

Python requires Polars 1.43.2 or later and PyArrow 23.0.1 or later. Both minimum
readers are tested against the same saved floating-point Parquet output. Rust
embedders using only CSV and Parquet can disable the adapter's default features
to omit the bundled ReadStat C backend. The Python and R packages include
ReadStat and retain SAS binary input support.

Rust diagnostic values use `yamaa_core::json::{Value, Number, Map}`. These owned
types preserve exact number spellings without requiring the `serde_json`
`arbitrary_precision` feature; serialized diagnostics keep their existing form.

Numeric operations use PortableLibmV1 with pinned libm 0.2.16. EXP/LN/POWER and
their downstream predicates, conversions and saved bytes can differ from
historical platform math; universal correct rounding is not promised.

The shared `domain`, `check` and `define` engine calls enforce fixed boundary
limits: 8 MiB per specification file, 10 GiB per input or saved file, 10 million
rows and 640 million cells per table, a per-match regex step limit and a cap of
10,000 reported findings. The
[resource policy](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md#resource-limits)
also states the structural limits. These are logical admission limits, not
reserved process memory. Standalone Python ODM helpers retain their own parser
options. Required third-party license notices travel with every package.
