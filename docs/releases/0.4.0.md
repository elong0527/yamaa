# yamaa 0.4.0

yamaa 0.4.0 is a fresh release. Python and R use one shared Rust engine
(`yamaa-core`, `yamaa-adapters` and the `yamaa` facade crate) for
specification admission, execution, verification, Define documents and
explicit Save. The packages ship as qualified wheels, a Python source archive
and an R source tarball attached to the GitHub release. The Rust crates remain
private and are included in both source packages. Breaking changes against
0.3.0 are listed under [Migration](#migration).

## Language

### Every specification is pruned after composition

After composition, the resolver removes the declarations that cannot affect
the artifact or a declared assertion, and runs name and reference validation
only afterwards. This now applies to every entry file: a file that declares
no `parents` is a composition of one layer, itself, and is composed, pruned
and validated on the same terms as a multi-layer composition. `parents: []`
is no longer a switch. Reachability begins with the columns named by
`output.columns`, `keys` and `output.order_by`, the columns and intermediates
that verifications read or carry, every row template and the dataset named by
`base`, and follows every semantic reference from there. Dead entries are
removed from `input`, `intermediates` and `columns`. An unresolved reference
reachable from a root still fails; one contained only in a dead declaration
is discarded with that declaration and is not an error. Composition orders
the resolved columns only when `parents` is declared; otherwise declaration
order is the resolved order. Rules:
[REQ-0614](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/specification/composition.md#req-0614),
[REQ-0638 to REQ-0641](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/specification/composition.md#req-0638)
and
[REQ-0060](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/execution/lifecycle.md#req-0060)
(#2696).

### `str_replace`

`str_replace` replaces every non-overlapping match of a portable regular
expression with literal text:

```yaml
derivation:
  str_replace:
    source: AE.AESPID
    pattern: '[^0-9]'
    replacement: ""
    missing: null
```

The scan is global and runs left to right. Each step keeps the match the
search rule keeps among the matches that start at or after the scan position,
and the next step starts where that match ends. Every step matches against
the whole source, so `^` matches only before the first scalar and a
lookbehind reads the text before the scan position. After an empty match the
scan moves one scalar forward and copies that scalar unchanged: with pattern
`x*` and replacement `-`, `ab` becomes `-a-b-`. `replacement` is literal
text: `$1`, `$&`, backslashes and braces are copied as written. A source the
pattern matches nowhere is returned unchanged; an empty result is the empty
string, never missing. A missing source returns `missing` or, without that
handler, fails as `missing_input`; a non-string source fails as
`incompatible_input_type`; an invalid pattern fails as `invalid_regex` at
`.pattern` before any input is read. The scan of one value is one match call
under the fixed regex step limit. Rules:
[REQ-1318 to REQ-1322](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/text.md#req-1318);
benchmarks `schema-str-replace` and `negative-str-replace-invalid-regex`
(#2775).

### `date_impute.not_after`

`date_impute` gains `not_after`, the upper bound that mirrors `not_before`.
A bound moves only the components imputation supplied, never a collected one,
and a complete source date is returned unchanged. A completed date on or
before `not_after` stands; otherwise the result is the latest day the
collected month or year admits that is on or before the bound. When no day in
the collected interval satisfies the bound, the result is missing and no
handler is invoked. A missing bound is no bound. Both bounds may be declared:
the result is then the completed date when it lies between them, otherwise
the nearest admitted day between them, and missing when they leave no day in
the interval, including a `not_after` earlier than `not_before`. Rules:
[REQ-1323 to REQ-1325](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/temporal.md#req-1323);
benchmark `adam-adcm-end-date-bound` (#2780).

### Row defaults are promoted per template

The engine promoted row defaults globally: a need in one row template
promoted the default for every template, so a candidate that another
template's filter suppressed could read a named lookup before suppression
and fail as `unmatched_key` on a lookup it never needed. Promotion needs are
now tracked per template. A column can be row-phase for the templates that
need it and column-phase for the rest, and the column phase skips the cells
the row phase completed. A candidate suppressed by a template filter never
reads a lookup it does not need
([REQ-1264](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/lookup.md#req-1264)).
No rule text and no benchmark data changed (#2754).

### `check` reports formula findings

`check` now reports, without reading inputs, the formula findings that
`domain` reports at validation: a formula that reads a column declared later
([REQ-0071](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/execution/lifecycle.md#req-0071)),
a qualified name that is not a declared record lookup
([REQ-0442](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/computation.md#req-0442))
and a cycle among formulas
([REQ-0072](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/execution/lifecycle.md#req-0072)).
Findings that need the inputs, or that come from other derivation kinds,
remain build findings (#2795).

## Hosts

### Public API

The Python package exports `domain`, `check`, `define` and
`resolve_specification`, their result and error types (`DomainError`,
`DefineError`, `ResolvedSpecification` and `ResolvedSpecificationError`), the
diagnostic record types `Diagnostic` and `SourceSpan`, `__version__`, and the
ODM helpers `read_odm` and `write_odm_parquet`. `resolve_specification`
produces the retained `ResolvedSpecification` artifact and raises
`ResolvedSpecificationError`. The R package exports `yamaa_domain`,
`yamaa_check`, `yamaa_define`, `yamaa_resolve_specification` and
`yamaa_read_resolved_specification`; its argument failures signal
`yamaa_argument_error`, and a failed Save signals `yamaa_domain_error` or
`yamaa_define_error`. Legacy Python evaluators, probes and IO/authoring
extensions, and `cdiscbuilder` are removed. Build holds results without
publishing; explicit Save publishes the retained bytes. Integers preserve the
complete signed 64-bit range and missingness separately in both hosts; R uses
`yamaa_int64_vector` for integer columns and `yamaa_utf8_vector` for text
containing NUL.

### Named diagnostic records

Every result carries its findings in two views built from one native record,
so the views cannot disagree and neither host parses JSON text.

In Python, `diagnostics` is a list of frozen `yamaa.Diagnostic` records with
`phase`, `condition`, `requirement` (`None` when the cause cites none),
`spec_paths`, `context`, `source_span` and `operand_route`. `context` is
structured: integer tokens are `int` with their exact value whatever their
width, other numbers `float`, objects `dict`, arrays `list`, text `str` and
null `None`. `source_span` is a `yamaa.SourceSpan(start, end)` with half-open
byte offsets into the original expression, and `operand_route` lists the
operand steps from the expression root to the failing node; both are `None`
when the failure site recorded no geometry, while `SourceSpan(0, 0)` and `[]`
are recorded zero geometry. `issues` stays the five-column Polars frame
(`phase`, `condition`, `requirement`, `spec_paths` and `context` as canonical
JSON text) and is a documented projection of the same records. `domain`,
`check` and `define` results, `DefineError` after a failed save and
`ResolvedSpecificationError` carry both views.

In R, `diagnostics` is an unnamed list of records with the same seven names.
`requirement` is `NULL` when absent. Context objects are named lists, arrays
are unnamed lists, text is character, logicals are logical and `null` is
`NULL`. An integer token whose magnitude is at most 2^53 becomes a double; a
wider integer token is carried as its exact decimal spelling in a character
scalar. Text containing NUL is a `yamaa_utf8` scalar. `source_span` is
`list(start, end)` or `NULL`; `operand_route` is a character vector,
`character(0)` for a failure at the root, or `NULL`. `issues` stays the data
frame with JSON-text `context`. `yamaa_domain`, `yamaa_check` and
`yamaa_define` results, `yamaa_define_error` after a failed save and
`yamaa_resolved_specification_error` carry both views. The
[Python](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/python/README.md#diagnostics)
and
[R](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/R/yamaa/README.md#diagnostics)
guides describe the record shapes (#2676).

### Host resource resolvers

Python `domain` and `check` accept a keyword-only `resolver=` argument backed
by the `yamaa.resources` module: `ResourceResolver`, `MemoryResolver` and
`SyntheticRemoteResolver`, with the `ResourceRequest`, `ResourceResult`,
`ResourceProvenance` and `ResourceFailure` types. R exposes the same surface
as `yamaa_resource_resolver`, `yamaa_memory_resolver`,
`yamaa_synthetic_remote_resolver`, `yamaa_resource_result` and
`yamaa_resource_failure`, passed as `resolver=` to `yamaa_domain` or
`yamaa_check`. `MemoryResolver.put` and `put_frame` refuse, at the call, a
key or reference that is not a non-empty string without NUL (`TypeError` or
`ValueError`) instead of storing an object no capture can reach.

### Arrow views

Build results expose Arrow C Stream views in both hosts. In Python,
`output_arrow`, `verification_log_arrow` and `warning_log_arrow` return
PyArrow tables through the Arrow PyCapsule interface. In R, the corresponding
read-only attributes return nanoarrow array streams and require nanoarrow
0.8.0 or later.

### Project environments and resources

Pass project `environment` files explicitly and use their current function
contracts and tests. A packaging `lock` is optional: without one, activation
still binds every called function and runs all its conformance cases, while
skipping package-version checks. A declared lock is required to exist and
pass verification; regenerate older project locks for 0.4.0. Metadata
diagnostics retain authored declaration paths and original failure facts.

Relative resources resolve from their declaring YAML file by default. An
input or output declaration may select `relative_to: entry` to share program
layers across studies while reading and saving beside each study's entry. For
an input, the selected base applies to both `path` and `schema`; each linked
producer uses its own entry. Output selection also applies to warning and
verification logs. Absolute paths retain their written destination. These
explicit choices replace the old project-root and data-root discovery; Save
still publishes the bytes retained by Build.

Python `__version__` comes from the installed distribution metadata and falls
back to the compiled core version when that metadata is absent, so a vendored
copy of the package imports.

## Engine

### The `yamaa` facade crate

The `yamaa` crate in `rust/crates/yamaa` is the only supported Rust surface.
An embedder configures one `Engine` from `EngineOptions` and calls `check`,
`build`, `define` and `resolve_specification` on it. `build` returns a `Build`
whose `report()` is a `Report` of typed `Diagnostic` records and whose
`save()` publishes through the resolver. All physical access goes through a
`ResourceResolver`; `MemoryResolver` serves specification bytes and Arrow
input frames from memory, and local files are the default resolver. Results
are Arrow `Table`s, and a `CancellationToken` stops an operation. Diagnostic
`context` is a `DiagnosticContext` of `ContextValue`s that keep integer
tokens exact (`Int`, `Uint`, or `Wide` with the decimal spelling of a token
outside both 64-bit ranges), with `source_span` and `operand_route` optional
and absent when unrecorded.

Every operation on `Engine` carries a runnable rustdoc example (`cargo doc
-p yamaa --no-deps` from `rust/`), and `rust/crates/yamaa/examples/memory.rs`
runs one specification entirely from memory, gated by
`rust/crates/yamaa/tests/memory.rs` (`cargo run -p yamaa --example memory`).
The committed API inventory `rust/crates/yamaa/public-api.txt` is compared by
`make check-repository`, and the
[design note](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rust/README.md#public-rust-api-design)
records the handle, ownership and stability rules. `yamaa-adapters` and
`yamaa-core` are internal and may change in any release. All crates stay
`publish = false`; depend on the facade by path or git.

The facade forwards the adapter features `yaml`, `parquet` and `readstat`.
They are independent and all enabled by default; each can be disabled
separately. Embedders using CSV and Parquet without SAS input can set
`default-features = false` and `features = ["parquet"]` to omit the bundled
ReadStat C backend. The Python and R packages enable all three and retain SAS
binary input support.

### Structured diagnostics in the adapters

The adapter diagnostic record carries context as an owned structured value
tree instead of JSON text and keeps the `source_span` and `operand_route`
geometry the core records. Integers beyond the 64-bit ranges survive without
narrowing. Geometry is present only when it was recorded, so diagnostics
without geometry keep their existing serialized form and no benchmark
expected output changed (#2675).

### Keyed intermediate lookups

A keyed intermediate is served by a donor index built once per build attempt
over the full key tuple: any number of key columns and any scalar key type,
including an `int` key matched against a `float` donor column or the
reverse, with donor read order kept inside each key bucket. Before, only a
lookup with exactly one string key was indexed, so `int` and composite keys
scanned the whole donor for every output row. 100,000 output rows against a
100,000-row donor now take 0.19 s with an `int` key and 0.26 s with a
`[str, int]` key, from 261 s. Expression keys, ranges, derivations,
correlated filters, `SELF` sources and donor relations below the
small-relation threshold still scan. Indexed and scanned lookups keep the
same diagnostics and ordering; the
[release guide](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md#keyed-intermediate-lookups)
lists the shapes (#2793).

### Windows

Two Windows-only failures are fixed. The memory-resolver route judged
declaring identities with the host's absolute-path rule, under which a
prefix-less root such as `/spec.yaml` is not absolute on Windows, so
inheritance families failed as `engine_rejected`; a lexical rule now treats
`/...` and drive-rooted `X:/...` spellings as absolute on every host (#2769).
Canonical adapter paths no longer carry the `\\?\` verbatim prefix, so
recorded origins, roots and resource paths have the same spelling as on the
other hosts and pass the resource grammar; the prefix is kept only for a path
Windows cannot address without it (#2807).

### Numeric behavior and limits

Numeric operations use PortableLibmV1 with pinned libm 0.2.16. EXP/LN/POWER
and their downstream predicates, conversions and saved bytes can differ from
historical platform math; universal correct rounding is not promised.

The shared `domain`, `check` and `define` engine calls enforce fixed boundary
limits: 8 MiB per specification file, 10 GiB per input or saved file, 10
million rows and 640 million cells per table, a per-match regex step limit
and a cap of 10,000 reported findings. The
[resource policy](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md#resource-limits)
also states the structural limits. These are logical admission limits, not
reserved process memory. The standalone Python ODM helpers retain their own
parser options. Required third-party license notices travel with every
package.

## Tooling

- Both hosts' native declarations are generated from
  `rust/interface/bindings.yaml` by `tools/packaging/generate_bindings.py`:
  Python's `_native.pyi` and PyO3 registration, and R's extendr registration
  fragments under `rust/crates/yamaa-r/src/generated/` and the private
  `.native_*` wrappers in `R/yamaa/R/native-bindings.R`.
  `make check-repository` and the `native-rust` job of the native
  qualification lane compare the generated files with the definition, so
  drift fails the pull request and the release run (#2691, #2693). Callable
  implementations and public package presentation stay handwritten; the
  [shared host interface](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rust/interface/README.md)
  describes the definition.
- The facade API inventory `rust/crates/yamaa/public-api.txt` is generated
  by `tools.packaging.generate_facade_api` and compared in the same check.
- The Python build backend refuses a non-table `[patch]`,
  `[patch.crates-io]` or `[workspace]` section and a malformed `members`
  list in the workspace `Cargo.toml` with `ValueError` instead of an
  unhandled exception.

## Migration

### From 0.3.0

- **Dead declarations no longer fail a flat file.** A declaration nothing
  reaches, such as a column outside `output.columns` that no derivation or
  verification reads, an intermediate no column reads, or an input no live
  declaration reads, is discarded before name and reference validation in
  every file, as it already was in a file with `parents`. A flat file that
  failed only because of an invalid reference inside such a declaration now
  builds. To keep a declaration validated, make it live: name the column in
  `output.columns`, `keys` or `output.order_by`, read it from a live
  derivation or verification, or name the dataset in `base`. An input no
  column reads is discarded too, so a specification whose driver was implied
  only by that input needs `base` to keep its driver. `parents: []` can be
  removed; it changes nothing.
- **Row templates.** A build that failed as `unmatched_key` on a candidate a
  template filter suppressed now builds; a lookup is read only by the
  templates that need it.
- **Diagnostics.** The `issues` frame keeps its five columns and JSON-text
  `context`. Code that parsed that text can read the `diagnostics` records
  instead: structured `context`, `source_span` and `operand_route`.
- **Rust embedders** depend on the `yamaa` facade crate. Paths into
  `yamaa-adapters` and `yamaa-core` are not supported.

### From 0.2.0 and earlier

The 0.4.0 upgrade also includes the language and environment changes
introduced before 0.3.0: `assert: {when: W, require: T}` replaces
`implies`, function calls drop `contract_version`, environments declare
`schema_version`, `language`, the project `lock` and inline function
definitions, environments are passed explicitly, and resources resolve from
their declaring YAML file. The
[migration table](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md#specification-and-environment-migration)
lists each earlier spelling and its current form.

## Supported platforms and readers

Supported platforms are CPython 3.12, 3.13 and 3.14 on Linux x86_64, macOS
arm64 and Windows x64, and R 4.6.1 source builds on those hosts. Each
attached wheel is the exact artifact tested on all supported interpreters for
its OS. The attached Python sdist and R tarball are the exact archives tested
on Linux; native CI separately qualifies source builds from each host's
archive on macOS and Windows. Free-threaded Python, musl and R binary
packages are not supported.

Python requires Polars 1.43.2 or later and PyArrow 23.0.1 or later; both
minimum readers are tested against the same saved floating-point Parquet
output. The minimum independent readers of saved artifacts are:

| Reader | Minimum |
| --- | --- |
| Python Polars | 1.43.2 |
| Python PyArrow | 23.0.1 |
| R arrow | 23.0.1 |
| R nanoarrow (Arrow views) | 0.8.0 |
| R jsonlite | 2.0.0 |
| Python lxml | 6.1.0 |

The Rust workspace builds with Rust 1.90.0 and the canonical `Cargo.lock`:
Arrow and Parquet 60.0.0, flatbuffers 25.12.19, libm 0.2.16 and the
reviewed vendored `saphyr-parser` 0.2.1 compact-flow patch, which is part of
every supported dependency graph. Cargo dependency floors stay where they are
tested; the crates are not published. The
[release guide](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md)
owns the complete platform, reader and dependency statements.

## Installation

Download the wheel for your platform, then install it with
`python -m pip install ./yamaa-0.4.0-<wheel-tags>.whl`. For a Python source
build, use `python -m pip install ./yamaa-0.4.0.tar.gz`. For R, use
`install.packages("yamaa_0.4.0.tar.gz", repos = NULL, type = "source")`.
Source installation needs Rust 1.90.0/Cargo, a C compiler and GNU make;
Windows R also needs Rtools45 and the `x86_64-pc-windows-gnu` Rust target. R
needs no Python runtime. R is distributed through the GitHub source asset;
CRAN, r-universe and R binaries are later work. These GitHub assets do not
establish PyPI publication. Host usage lives in the
[Python](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/python/README.md)
and
[R](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/R/yamaa/README.md)
guides.

## Deferred to 0.5.0

The reusable compile-once plan handle, partitioned and streaming execution
with cancellation, the version and feature handshake runtime with its ABI
tests, nearest-date selection and the replacement of the vendored YAML
parser patch are planned under #2785. The Polars floor stays 1.43.2; it
moves only through a plain dependency bump if the Parquet writer's
floating-point column metadata becomes optional upstream.
