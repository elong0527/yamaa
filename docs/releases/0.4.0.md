# yamaa 0.4.0

yamaa 0.4.0 is a fresh release with breaking changes. Python and R now run one
shared Rust engine for specification admission, execution, verification,
Define documents and explicit Save, through the same small API of spec and
project objects. Read [Migration](#migration) before you upgrade.

## Install

0.4.0 is distributed only as assets of the GitHub release tagged
`yamaa-v0.4.0`: one Python wheel per supported OS, the Python source archive
`yamaa-0.4.0.tar.gz` and the R source archive `yamaa_0.4.0.tar.gz`. These
GitHub assets do not establish PyPI publication. CRAN, r-universe and R binary
packages are later work.

```sh
python -m pip install ./yamaa-0.4.0-<wheel-tags>.whl
python -m pip install ./yamaa-0.4.0.tar.gz   # Python source build
```

```r
install.packages("yamaa_0.4.0.tar.gz", repos = NULL, type = "source")
```

The Linux wheel is `manylinux_2_34` and needs glibc 2.34 or later, for example
RHEL 9, Ubuntu 22.04 or Debian 12; older systems build from
`yamaa-0.4.0.tar.gz`. Each wheel is the exact artifact tested on every
supported interpreter for its OS. The attached source archives are the ones
tested on Linux; native CI also qualifies source builds on macOS and Windows
from each host's own archive.

Source builds need Rust 1.90.0 with Cargo, a C compiler and GNU make. They
download the locked Rust crates from crates.io, and pip's build isolation
fetches `maturin`, so an offline build needs a pre-filled Cargo cache. Windows
R builds also need Rtools45 and the GNU target on the pinned toolchain:
`rustup toolchain install 1.90.0 --target x86_64-pc-windows-gnu`. The bundled
`rust-toolchain.toml` forces Rust 1.90.0, so a target added to another
toolchain is not used. R needs no Python runtime.

The `yamaa` project on PyPI holds only the outdated 0.1.0, so
`pip install yamaa` installs a stale API; install 0.4.0 from the release
assets (#2932).

Every package carries the project's MIT license as `LICENSE.txt`. It also
carries `LICENSE-THIRD-PARTY.txt`, with the license, copyright and NOTICE texts
of every third-party Rust crate in the locked build graph, alongside the
ReadStat, Unicode and YAML parser notices. Wheels keep these files in
`yamaa-0.4.0.dist-info/licenses/`, the Python source archive keeps them at its
root, and the R package installs them from `inst/`. The wheels link Apache-2.0
Arrow, Parquet, FlatBuffers and Thrift crates and BSD-3-Clause compression
crates, so the Python license expression is
`MIT AND Apache-2.0 AND BSD-3-Clause AND Unicode-3.0` (#2926).

## Supported platforms and dependencies

- CPython 3.12, 3.13 and 3.14 on Linux x86_64, macOS arm64 and Windows x64.
- R 4.6.1 source builds on the same three hosts.
- Free-threaded Python, musl and R binary packages are not supported.

Python requires Polars 1.35.2 or later and PyArrow 23.0.1 or later. The
minimum independent readers of saved artifacts are:

| Reader | Minimum |
| --- | --- |
| Python Polars | 1.35.2 |
| Python PyArrow | 23.0.1 |
| Python lxml | 6.1.0 |
| R arrow | 23.0.1 |
| R jsonlite | 2.0.0 |

Both packages build the Rust workspace with Rust 1.90.0 and the canonical
`Cargo.lock`, including Arrow and Parquet 57.3.0, libm 0.2.16 and the vendored
`saphyr-parser` 0.2.1 with its reviewed compact-flow patch. Arrow and Parquet
are pinned to exactly 57.3.0, with brotli 8.0.4 and lz4_flex 0.13.1 floors, so
an embedder whose Rust graph holds Arrow 57.3 builds the engine unchanged
(#2831, #2832). Saved Parquet records only type-defined column orders, which
Polars 1.35.2 and later read (#2833). The
[release guide](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md)
has the complete platform, reader and dependency statements.

## Language

### Every specification is pruned

Every specification is composed and pruned before name and reference
validation, whether or not it declares `parents`. A file without `parents` is
a composition of one layer. Pruning removes the `input`, `intermediates` and
`columns` entries that cannot affect the artifact or a declared assertion. An
unresolved reference reachable from a root still fails; one inside a removed
declaration is discarded with it. `parents: []` no longer affects pruning.
Any `parents` field, even an empty one, still orders resolved columns by
dependency
([REQ-0643](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/specification/composition.md#req-0643)).
Rules:
[REQ-0614](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/specification/composition.md#req-0614),
[REQ-0638 to REQ-0641](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/specification/composition.md#req-0638)
and
[REQ-0060](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/execution/lifecycle.md#req-0060)
(#2761).

### `str_replace`

`str_replace` replaces every match of a portable regular expression with
literal text:

```yaml
derivation:
  str_replace:
    source: AE.AETERM
    pattern: '\s+'
    replacement: " "
```

- The scan is global and runs left to right; matches never overlap.
- `replacement` is literal text: `$1`, `$&`, backslashes and braces are copied
  as written.
- After an empty match, the scan copies the next character unchanged and
  continues after it: pattern `x*` with replacement `-` turns `ab` into
  `-a-b-`.
- A source with no match is returned unchanged, and an empty result is the
  empty string, never missing. A missing source returns the declared
  `missing` value.

Rules:
[REQ-1318 to REQ-1322](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/text.md#req-1318)
(#2776).

### `date_impute.not_after`

`date_impute` accepts `not_after`, the upper bound that mirrors `not_before`.
A bound moves only the components that imputation supplied, and a complete
source date is returned unchanged. A completed date after the bound becomes
the latest day the collected month or year allows on or before the bound.
When no such day exists, the result is missing and no handler runs. Both
bounds may be declared together. Rules:
[REQ-1323 to REQ-1325](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/temporal.md#req-1323)
(#2781).

### Datetimes recorded to the hour or minute

`datetime_impute` and `datetime_precision` read source text recorded to the
hour (`2025-03-04T08`) or the minute (`2025-03-04T08:30`), as ISO 8601
reduced precision allows. `datetime_precision` returns `D`, `H`, `M` or `S`
for a source collected to the day, hour, minute or second, so a `case` on it
derives the ADaM `*TMF` flag. `datetime_impute` keeps every collected field
and supplies only the missing ones: `first` supplies `00`, and `last`
supplies `23`, `59` and `59`. Converting or ingesting text as a `datetime`
column is unchanged: `T08:30` still names second zero and `T08` is still not
a `datetime`. Rules:
[REQ-1326 to REQ-1329](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/temporal.md#req-1326)
(#2818).

### Row defaults are promoted per template

A row default is promoted only for the row templates that need it. A
candidate that a template filter suppresses never reads a lookup it does not
need, so it no longer fails as `unmatched_key`
([REQ-1264](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/lookup.md#req-1264))
(#2762).

One limit remains. When the templates that still need a column read
different drivers, the column is bound against the whole dataset rather than
against each template's own driver. A derivation in one of those templates
that reads a stored field only its own driver supplies can still fail key
validation. #2829 tracks removing this limit in 0.5.0.

### `check()` reports formula findings

For a specification without `rows`, `check()` now reports three findings that
`run()` reports at validation, without reading inputs: a formula that reads
a column declared later (`forward_reference`,
[REQ-0071](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/execution/lifecycle.md#req-0071)),
a qualified name that is not a declared record lookup
([REQ-0442](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/computation.md#req-0442)),
and a cycle among formulas
([REQ-0072](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/execution/lifecycle.md#req-0072)).
Findings that need the inputs or come from other derivation kinds are still
reported by `run()` only (#2796).

### A qualified `between.value` names the row's driver

A `between.value` written as `INPUT.FIELD`, in a named intermediate or in an
aggregate, reads the record of the input that drives the row being matched:
the root `base` without row templates, or the row template's `dataset`. Inside
another intermediate's `derivations`, the reading intermediate's dataset
supplies it. Any other input fails validation as `unknown_field` at that
`between.value`. This also applies when the intermediate is reached through
another `between.value` or an aggregate's `derive` step. The value is never
read through the implicit join.

Earlier, an intermediate compared a different field of the driver record, and
an aggregate read the named input at the driver's record positions. Both gave
wrong values with no message. `check()` reports the refusal for an aggregate;
for an intermediate, `run()` reports it (#2951). A row template driven by a
secondary input can now read its own driver in a `between.value` or a
correlated `filter`
([REQ-0121](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/lookup.md#req-0121),
[REQ-0472](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/operations/aggregation.md#req-0472))
(#2888, #2904, #2925).

### SAS records deleted in place are refused

A `.sas7bdat` input that still holds records deleted in place, for example
after `PROC SQL DELETE` or a DATA step `MODIFY` with `REMOVE`, fails as
`source_sas_invalid` with cause `deleted_records`. Earlier releases returned
the deleted records as rows. The finding's `hint` says to rewrite the dataset
first, for example with `PROC COPY` or a DATA step. A compressed dataset with
deleted records still fails with cause `compression`
([REQ-1317](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/storage/sas.md#req-1317))
(#2924).

## Python and R

### Public API

The Python package exports `spec`, `project`, `read_odm`, `Error` and
`__version__`. The R package exports `yamaa_spec`, `yamaa_project` and
`yamaa_read_odm`, and signals failures as `yamaa_error` conditions (#2967).
`spec(path)` opens one specification and `project(path)` a study's project
file. Neither reads anything until a method runs, and every method rereads the
files:

| Call | Returns |
| --- | --- |
| `spec.check()` | Static findings in `issues`, without reading study data. |
| `spec.resolve()` | The composed specification as a dict or named list. |
| `spec.run()` | A run: `output`, `issues`, `report` and `save()`. |
| `project.spec(name)` | The listed specification whose `domain` is `name`, with the project's codelists and functions. |
| `project.check()` | Static findings for every listed specification and the project. |
| `project.run(section)` | A project run of one section or all: `names`, one read-only run per specification (`runs["ADSL"]`, `runs[["ADSL"]]` in R), `issues`, `report` and `save()`. |
| `project.submission(section, created=)` | define.xml, and Dataset-JSON where a section asks for it: `issues` and `save()`. |

Results publish nothing until `save()`, which writes exactly what was built.
`check()` and `run()` return problems as issues rather than raising;
`save()`, `resolve()` and an unknown specification name or section raise
`yamaa.Error` in Python or a `yamaa_error` condition in R, carrying `issues`.
Python returns Polars DataFrames, and integers keep separate missingness in
both hosts and the full signed 64-bit range in Python. R returns data.frames
of plain double and character columns and passes project functions plain
values the same way; an integer beyond 2^53 or text containing NUL raises an
error instead of changing. R gains `yamaa_read_odm()`. The
[R and Python API](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/articles/api.md)
page shows every call in both languages.

### One issues table

Every finding is one row of the `issues` table, built in Rust and identical in
both hosts: `phase`, `condition`, `requirement`, `spec_paths`, `context` as
canonical JSON text, then `source_span`, the start and end byte offsets into
the failing expression, and `operand_route`, the operand steps from the
expression root to the failing node. Both are missing when the failure
recorded no place in an expression. The error a failed call raises carries the
same table.

### One run report

One run report replaces the verification and warning logs (#2912).
`output.report` replaces `output.verification_log` and `output.warning_log`,
and a run's `report` replaces its `verification_log` and `warning_log`. The
report has fourteen columns: one row for the run, then one per input, row
template, handler, output column and evaluated check. Every run that began
has one in memory; `save()` writes it to `output.report` before the dataset,
and a failed run's `save()` writes only the report. A violated warning appears
in the report and not in `issues`
([REQ-0392](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/execution/verification.md#req-0392)).

### Project files

A `project.yaml` lists a study's specifications by section, with the metadata
they share (#2967). Its `environments` names each language's environment file,
and `codelists`, `study` and the `sdtm`, `adam` and `send` sections move there
from the environment file. An environment file keeps `schema_version`, `lock`
and `functions`; the `environments` key states its language, so environment
files no longer declare `language`. A section needs only `specs` to run;
`study`, `standard` and `define` are required only to create submission
files, and `datasets: json` replaces `dataset_json: true`. A listed
specification's name is its `domain`, unique across the project
([REQ-1331 to REQ-1348](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rules/specification/project.md#req-1331)).

A project run builds each listed specification of the selected sections once,
in dependency order, and hands a producer's result in memory to the
specifications that link it through `schema`. A linked producer outside the
run is read from its saved file, so ADaM can be rerun against finished SDTM. A
failed specification stops only the specifications that read it. Saving checks
every target first and writes no dataset unless every specification succeeded.

### Environments and resource paths

Pass the project file explicitly; it is not discovered. An environment's
packaging `lock` is optional: without one, activation still binds every called
function and runs its conformance tests but skips package-version checks. A
declared lock must exist and pass verification.

Relative paths resolve from the YAML file that declares them: the project
file's from the project file and an environment file's from that file. An
input or `output` may set `relative_to: entry` to resolve from each study's
entry file instead, so shared program layers can read and save beside each
study. On an input it covers both `path` and `schema`; on an output it also
covers the run report. There is no project-root or data-root discovery.

## Rust

### The `yamaa` facade crate

The `yamaa` crate in `rust/crates/yamaa` is the supported Rust embedding
surface. Configure one `Engine` from `EngineOptions` and call `check`,
`build`, `define` and `resolve_specification`. A `Build` holds Arrow `Table`
results and a `Report` of `Diagnostic` records, and `save()` publishes through
the configured `ResourceResolver`: local files by default, or `MemoryResolver`
for bytes and Arrow frames held in memory. The operations behind the Python
and R packages are `Engine` methods too: `spec_check`, `spec_run`,
`spec_resolve`, `project_spec`, `project_check`, `project_run` and
`project_submission`, with `odm::read_odm` for ODM XML. `yamaa-adapters` and
`yamaa-core` are internal and may change in any release. The crates are not
published; depend on the facade by path or git.

The facade forwards the independent `yaml`, `parquet`, `readstat` and `odm`
features, all on by default. `default-features = false, features = ["yaml",
"parquet"]` omits the bundled ReadStat C build and the ODM XML reader; an
engine built without `yaml` admits no YAML specification. The Python and R
packages enable all four.

Cargo applies `[patch]` only in the root workspace being built, so an embedder
that depends on the facade by git or path gets the upstream `saphyr-parser`
instead of the reviewed compact-flow patch. Until #2583 lands, add the patch
next to the facade dependency, pointing at the vendored copy (#2929):

```toml
[patch.crates-io]
saphyr-parser = { path = "<yamaa checkout>/rust/vendor/saphyr-parser" }
# or, for a git dependency:
# saphyr-parser = { git = "https://github.com/elong0527/yamaa", tag = "yamaa-v0.4.0" }
```

Run `cargo doc -p yamaa --no-deps` and `cargo run -p yamaa --example memory`
from `rust/`; the
[design note](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rust/README.md#public-rust-api-design)
records the handle, ownership and stability rules (#2749).

### Generated host bindings

Both hosts' native declarations are generated from
`rust/interface/bindings.yaml`: Python's `_native.pyi` and PyO3 registration,
and R's extendr registrations and private `.native_*` wrappers.
`make check-repository` and the native qualification lane fail when the
generated files drift from the definition. Every native export names its
counterpart in the other host unless the definition declares it host
transport. Callable implementations and the public package APIs stay
handwritten. The
[shared host interface](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/rust/interface/README.md)
describes the definition (#2765, #2789, #2808).

## Performance

A keyed intermediate lookup is served by an index built once over its full key
tuple, for any number of key columns and any scalar key type, so integer and
composite keys no longer scan the whole donor for every output row. Results,
diagnostics and ordering are unchanged. The
[release guide](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md#keyed-intermediate-lookups)
lists the lookup shapes that still scan (#2798).

## Numeric behavior and limits

Numeric operations use PortableLibmV1 with libm 0.2.16. EXP, LN and POWER
results, and the predicates, conversions and saved bytes that depend on them,
can differ from platform math; correct rounding is not promised.

Every spec and project operation enforces fixed limits: 8 MiB per specification
file, 10 GiB per input or saved file, 10 million rows and 640 million cells per
table, a per-match regex step limit and 10,000 reported findings. The
[resource policy](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md#resource-limits)
lists every limit. These are logical admission limits, not reserved memory.

## Migration

### From 0.3.0

Each 0.3.0 Python call has one replacement:

| 0.3.0 | 0.4.0 |
| --- | --- |
| `yamaa.domain("dm.yaml", environment="python/environment.yaml")` | `yamaa.project("project.yaml").spec("DM").run()` |
| `yamaa.domain("dm.yaml")` | `yamaa.spec("dm.yaml").run()` |
| `yamaa.check("dm.yaml", environment=...)` | `yamaa.project("project.yaml").spec("DM").check()`, or `yamaa.spec("dm.yaml").check()` |
| `yamaa.define("environment.yaml", "sdtm", created=t)` | `yamaa.project("project.yaml").submission("sdtm", created=t)` |
| A loop over every SDTM or ADaM specification | `yamaa.project("project.yaml").run("sdtm")` or `.run("adam")` |
| `result.verification_log`, `result.warning_log` | `run.report` |
| `result.save()`, which returns `True` | `run.save()`, which returns nothing and raises `yamaa.Error` |
| `DomainError`, `DefineError` | `yamaa.Error`, carrying `issues` |
| `yamaa_domain(...)`, `DomainRun`, `DomainRunError` | `yamaa.spec(path).run()`, `yamaa.Error` |
| `generate_study_document(...)` | `yamaa.project("project.yaml").submission(section)` |
| `yamaa.odm` and the other subpackages | `yamaa.read_odm(path)`; the subpackages are private |

The R `cdiscbuilder` package is removed; the `yamaa` R package makes the same
calls through `yamaa_spec()`, `yamaa_project()` and `yamaa_read_odm()`.

- **Project files.** Move `codelists`, `study` and the `sdtm`, `adam` and
  `send` sections from the environment file into one `project.yaml`, name each
  language's environment file under its `environments`, and delete `language`
  from the environment files. Replace `dataset_json: true` with
  `datasets: json`.
- **Run reports.** Replace `output.verification_log` and `output.warning_log`
  with one `output.report`, whose fourteen columns replace the columns of both
  logs.
- **Dead declarations.** A dead declaration with an invalid reference no longer
  fails a flat file. To keep a declaration validated, make it live: name the
  column in `output.columns`, `keys` or `output.order_by`, or read it from a
  live derivation or verification. An input that no column reads is removed as
  well; if it was the implied driver, name it in `base`. `parents: []` no
  longer affects pruning. Any `parents` field still orders resolved columns by
  dependency, so remove it only once no column reads a column declared after
  it; otherwise `check()` and `run()` report `forward_reference`.
- **Datetime precision.** `datetime_precision` of text recorded to the minute
  returns `M` (was `S`), and `datetime_impute` with `time: last` completes it
  to second `59` (was `00`). Text recorded to the hour is now accepted (was
  `invalid_datetime_text`). `IN ('M', 'S')` selects what `= 'S'` selected in
  0.3.0, and only those forms convert directly to a `datetime`. Hour text,
  now accepted, returns `H`: a condition that means "a time was collected"
  tests `IN ('H', 'M', 'S')`, and hour text is completed with
  `datetime_impute` rather than converted.
- **Range values.** A `between.value` that names an input other than the
  row's driver now fails validation, in a named intermediate and in an
  aggregate. Earlier releases compared a wrong value with no message, so audit
  outputs built from such specifications. Derive the value into a column
  first, for example an `AGE` column from `DM.AGE`, and name that column:
  `between: {value: AGE, ...}`.
- **SAS datasets with deleted records.** Rewrite a `.sas7bdat` input that
  holds records deleted in place, for example with `PROC COPY`, before
  reading it.
- **Project locks.** Regenerate a project lock that pins an earlier yamaa
  before using project functions.
- **Issues.** The `issues` table keeps its five columns and adds
  `source_span` and `operand_route`; `context` stays canonical JSON text.
- **Rust.** Depend on the `yamaa` facade crate, not on `yamaa-adapters` or
  `yamaa-core`.

### From 0.2.0 and earlier

The 0.4.0 upgrade also includes the language and environment changes made
before 0.3.0: `assert: {when: W, require: T}` replaces `implies`, function
calls drop `contract_version`, environments declare `schema_version`, the
project `lock` and inline function definitions, the project file links them
explicitly, and resources resolve from their declaring YAML file.
The
[migration table](https://github.com/elong0527/yamaa/blob/yamaa-v0.4.0/docs/release.md#migration)
lists each earlier spelling and its current form.

## Known issues

- In a row template driven by a named intermediate, derive every column
  inside the template. A column-level derivation fails as `engine_rejected`
  with code `result_projection` (#2930).
- An `engine_rejected` finding with code `result_projection` and no
  requirement marks a specification shape the engine does not support yet.
  Please report it (#2889).
- Some valid Parquet files are refused (#2940):
  - files with more than 32,768 row groups;
  - DuckDB integer columns annotated `Int(64, signed)`;
  - string columns whose embedded Arrow schema says `string_view` or
    `dictionary`, as pyarrow string views and Polars `Categorical` or `Enum`
    columns write them. Cast them to plain strings before writing.

## Deferred to 0.5.0

The reusable plan handle, partitioned and streaming execution, the version
and feature handshake with its boundary tests, nearest-date selection and
replacing the vendored YAML parser patch are planned in #2785. Reading a SAS
dataset that holds records deleted in place, returning only its live records,
follows #2924.
