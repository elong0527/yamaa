# yamaa 1.0.0

yamaa 1.0.0 freezes the user interface: a project, program or script that
works with 1.0.0 works the same way, with the same results and saved bytes,
in every later 1.x release, as [Stability](#stability) says (#3030 D1).
1.0.0 breaks with 0.5.0, so read [The break from 0.5.0](#the-break-from-050)
before you upgrade.

## The break from 0.5.0

Every file written for 0.5.0 must be rewritten. A 1.0 file starts with
`yamaa: "1.0"` and `type:`, and some fields and values are spelled
differently, but the language still means what it meant: a rewritten
specification builds the datasets that 0.5.0 built, apart from the changes
that this section and [Changes since 0.5.0](#changes-since-050) list.
Python's tables and lint, the issues table, some condition names and the Rust
facade change too.

The approved rename table lists every changed spelling:
[`tools/migrate/renames.yaml`](https://github.com/elong0527/yamaa/blob/yamaa-v1.0.0/tools/migrate/renames.yaml)
at the 1.0.0 tag. For every field, keyword and enumerated value of the 0.5.0
schemas it gives the 1.0 spelling, or the reason the item was removed, and it
lists the fields that 1.0 adds and the conditions, diagnostic paths and
issues-table columns that change (#3030 D27, D58). There is no migration
guide and no converter for users (#3030 D35): rewrite each file with the
table. The converter that moved this repository's own files was internal,
shipped in no package and left the repository before 1.0.0 (#3443).

### Files

- **Header.** Every file starts with `yamaa: "1.0"`, the oldest language
  version that it needs, quoted, and `type:`, one of `spec`, `project`,
  `codelists` and `function`, in place of `schema_version` (SCHEMA-2,
  #3030 D4).
- **Functions.** A project function is one `type: function` file, listed in
  the project's `functions`, with each host's callable under
  `implementations`. The project's `environments` holds each host's lock, as
  `python: {lock: uv.lock}`, and the two environment files are gone (#3030
  D8).
- **Expressions.** An expression field takes one grammar: a bare name reads a
  variable, text is quoted, as in `derivation: "'DM'"`, and a YAML number or
  Boolean is a literal, so `literal`, `compute` and the string form of
  `source` are gone. YAML `null` is the missing value, and a child layer
  clears an inherited field by listing its path under `clear:`, not by
  setting it to null. Value fields, such as handlers, `dict` values and `cut`
  labels, keep bare text (#3030 D18, D31).
- **Inheritance.** A child that restates an inherited `input`,
  `intermediates` or `rows` member, or a named window, merges with it as in
  0.5.0: a mapping key by key, so an entry the child leaves out comes back
  from the parent. Listing the mapping in `clear` beside it, as
  `clear: [rows.scores.derivations]`, replaces it instead, and the lint
  reports a restatement that leaves entries out as `partial_restatement`
  (LAYER-6, LAYER-8, LAYER-9, #3689).
- **Fragments.** A layer lists reusable spec fragments under `include:`. At
  each layer its parent chain contributes first, then its fragments in list
  order, then its own fields, so one fragment file serves every template that
  lists it. A fragment names neither `parent` nor `include`
  (`prohibited_construct`), an `include` that leads back to a layer still
  being composed is an `inheritance_cycle`, and a file reached twice in one
  composition fails as the new `duplicate_layer` (LAYER-3, LAYER-4, #3688).
  `check(parent = )`, and `yamaa check PATH --parent PATH`, check a fragment
  as if a template you name were its parent, as it would compose in a file
  that names the template as its `parent`, includes the fragment and writes
  nothing else, so a fragment is checked before any file lists it; a
  `parent` given for a file that declares `parent` or `include` is refused as
  `value_not_permitted` at `parent` (LAYER-4, #3694).
- **Lookups.** A named intermediate declares its `key`, unless it drives a
  row template, and an implicit join, or a qualified aggregate without its
  own `key`, matches on the `key` that its input declares instead of on
  same-named columns. `absent` answers only a lookup that finds no record: a
  read of a variable that does not exist fails as `unknown_field` (#3030
  D23, D63, D67).
- **CDISC metadata.** A project section lists `standards`, and a column or
  value-level entry lists `origins`, as Define-XML allows several. A
  specification with submission metadata names its `model`, `SDTM`, `SEND`
  or `ADaM`, and a `copy` entry takes columns from a producer linked through
  `schema`, with the type and label that the producer declares and a
  Predecessor origin (#3030 D16, D19, D25, D70).
- **Renamed fields.** Some operands, handlers and bindings are renamed, such
  as `study_day`'s `date` to `source`, an intermediate's `no_match` to
  `absent`, an aggregate's `derive` list to a `derivations` map, `diff`'s
  `bounds` to `closed`, and a project section's `datasets` to `transport`,
  with `json` spelled `dataset_json` (#3030 D58).
- **A specification alone.** A specification checked or run without its
  project file fails validation at each codelist and inventory vocabulary
  that it binds and each project function that it calls; 0.5.0 skipped or
  deferred those checks (CT-13, #3030 D32).

### Python, R and diagnostics

- **Python tables.** Every table is a `yamaa.Table`, which implements the
  Arrow PyCapsule stream interface and converts with `to_polars()`,
  `to_pandas()`, `to_arrow()` or `to_pylist()`. The package has no runtime
  dependencies, so install Polars, pandas or PyArrow to convert to their
  tables; `to_pandas()` keeps each column's Arrow type (#3030 D11, D43, D190).
  R's tables stay data frames.
- **Saving.** `save()` returns the paths that it wrote, and a refused save's
  `yamaa.Error`, or R's `yamaa_error` condition, carries `paths` (#3030 D38,
  D69).
- **Status and printing.** Every result has a `status`: `succeeded`,
  `failed`, or `skipped` for a project run's specification whose producer did
  not complete. A result, and a specification or project object, prints the
  summary that the engine renders, the same words in both hosts and on the
  command line: Python's `repr()` returns it, and R's `format()` returns its
  lines and `print()` writes them, where R printed a bare environment (#3030
  D36, D37, D103, #3401).
- **Engine information.** `yamaa.info()` and R's `yamaa_info()` return the
  engine version, the language versions that it reads, its features, the
  host, the host's version and the platform, as a dict or a named list: the
  record that a selftest's `info` holds and that `yamaa --version` prints.
  `__version__` and `packageVersion("yamaa")` stay the package versions
  (#3030 D41, #3404).
- **Project names and creation time.** A project's `names` lists its
  specifications in the order that a run of every section builds them,
  without reading study data, and a submission's `created` gives the creation
  time that its documents carry: the one given, or the time it read once for
  every section (#3030 D45, D69, D129, D180, #3405).
- **R names and length.** `names()` of an R result lists its fields and
  methods, starting with `status`, where it listed its hidden handle, and
  `length()` counts them; a project run's `names()` are its specifications'
  names. Python's `len()` of a project run counts them too (#3030 D44,
  #3406).
- **Lint.** `yamaa.lint()` and R's `yamaa_lint()` replace
  `python -m yamaa.style` and the Python package's `style` extra, and a
  suppression comment is spelled `# yamaa-lint: allow` (#3030 D40, D58).
- **Issues.** The issues table has twelve columns, in a new order that begins
  with `severity`. `rule` replaces `requirement` and cites a rule card, such as
  `CHECK-7`, as the run report's `RULE` column now does, instead of a
  `REQ-NNNN` ID; `severity`, `file`, `line`, `column` and `message` are new
  (#3030 D28, D59).
- **Conditions and paths.** Four conditions are renamed, such as
  `schema_version_mismatch` to `unsupported_language_version`, seven retire,
  and new ones arrive, such as `project_binding_missing`. Spec paths follow the
  renamed fields and name a row template or an intermediate by its `id`, as
  in `intermediates.<id>` instead of `intermediates[0]`. The rename table's
  `conditions` and `paths` blocks list these (#3030 D58, D69), and the changes
  below name each refusal that now reports a more specific condition, path or
  `context` key.

### The Rust facade

The `yamaa` crate, the Rust facade that both packages and the command line
call, changes throughout, and from 1.0.0 its public items are frozen as
[`rust/crates/yamaa/public-api.txt`](https://github.com/elong0527/yamaa/blob/yamaa-v1.0.0/rust/crates/yamaa/public-api.txt)
lists them. It keeps the 1.0 use cases and removes the pre-1.0 entry points:
a specification's and a project's operations are requests that
`Engine::spec(path)` and `Engine::project(path)` return, every operation fails
with one `Failure`, the crate root re-exports only what configures an engine
or comes back from one, and the two host ports move under `yamaa::host`.
[Rust facade](#rust-facade) below names each change (#3030 D22, D192, #3415,
#3765, #3766).

## Install

Install the Python package from PyPI with `python -m pip install yamaa`
(#3030 D57). The wheels cover CPython 3.12 and later on Linux x86_64 and
aarch64 with glibc 2.28 or later, macOS arm64 and Windows x64; elsewhere pip
builds the source archive, which needs Rust 1.82 or later and a C compiler.
Each GitHub release carries the same Python files, and also R binary packages
for Windows x64 and macOS arm64, for R 4.6 and R 4.5, which install without
Rust, Rtools or a network; the R source package, for Linux and any other R
from 4.2.0 (#3561); and the standalone `yamaa` command line for Linux,
Windows and macOS, which needs no Python, R or Rust and ships unsigned
(#3030 D52). The R source package also goes to CRAN (#3030 D50). The
[Python](https://github.com/elong0527/yamaa/blob/main/python/README.md#installation)
and [R](https://github.com/elong0527/yamaa/blob/main/R/yamaa/README.md#installation)
package pages give the commands,
[Supported platforms](https://elong0527.github.io/yamaa/release/#supported-platforms)
lists every platform, and
[Installing in a restricted environment](https://elong0527.github.io/yamaa/articles/restricted-environments/)
covers machines without internet access.

## Stability

From 1.0.0, every 1.x release keeps the 1.0 interface: the file types and
their fields, the Python, R and command-line calls and their results, the
Rust facade's public items, the condition and rule that a failure reports,
the columns of the issues table and the run report, and the bytes of each
saved file. A minor release may only add, such as an optional field or a new
function, and only a 2.0 release may break the interface. Fixing behavior
that contradicts a rule is not a break, and the notes of its release list
each fix. Messages are not frozen, so programs match `condition` and `rule`,
never `message` (#3030 D1, D20). The stability contract states it in full in
the [release guide](https://elong0527.github.io/yamaa/release/#stability-contract),
and from 1.0.0 the repository's checks refuse a change that breaks it.

## Known issues

- Nothing planned for 1.0.0 is deferred: every issue of its plan is in this
  release (#3673 D279, D280).
- The command-line binaries are unsigned and not notarized (#3030 D52). On
  macOS, clear Gatekeeper's quarantine attribute once; on Windows, SmartScreen
  may stop a downloaded `yamaa.exe` until you choose to run it.
  [Command-line binaries](https://elong0527.github.io/yamaa/release/#command-line-binaries)
  gives the steps.
- The YAML reader is a vendored copy of saphyr-parser 0.2.1, with a reviewed
  fix for compact flow pairs and 0.2.2's raw NUL fix, built as
  `yamaa-saphyr-parser`. The published saphyr-parser 0.2.2 fails four of the
  five compact-flow controls, splitting the nested mapping of
  `[k: {a: 1, b: 2}]` for example, so yamaa keeps its copy until a published
  release passes them. The
  [release guide](https://elong0527.github.io/yamaa/release/#components-outside-the-advisory-scanners)
  documents the vendored copy as supported (#3030 D229, #3682).

## Changes since 0.5.0

Each change since 0.5.0 that users can observe has one line below, by area:
the language first, then inputs, controlled terminology and submission
metadata, checking and diagnostics, files and saving, the lint and the command
line, the packages and platforms, and the Rust facade. The
[0.5.0 notes](https://github.com/elong0527/yamaa/blob/yamaa-v0.5.0/docs/releases/0.5.0.md)
list the changes up to 0.5.0.

### Language

- Every call reads language version 1.0: a specification, project, codelists
  or function file that declares `yamaa: "1.0"` and its `type` is checked,
  run, resolved, submitted and linted. `resolve()` records a 1.0
  specification's `language_version` in place of `schema_version` (#3030
  D75, D76 and D84, #3259).
- A file that declares `schema_version`, written for 0.5.0, is no longer
  read: it fails as `unsupported_language_version`, naming language version
  0.5, at its own `schema_version` when a call or `lint()` names it, and at
  `parent` or at the field that names it, such as a section's `specs`, a
  project's `functions` or `codelists`, or an input's `schema`, when another
  file reads it, as the Rust facade's `Engine::file_type` and the command
  line already refused it. A 0.5 project file is refused before any
  environment file it links is read, so `project_environment_missing` and
  `project_environment_invalid`, which only such a project raised, retire
  (their 1.0 names are `function_implementation_missing` and
  `function_file_invalid`, D58). A specification or project file that
  declares neither `yamaa` nor `schema_version` fails as
  `missing_required_field` at `yamaa`, where a specification failed as
  `schema_version_mismatch` and a project file as `missing_required_field`,
  each at `schema_version` (SCHEMA-2, LAYER-4, #3030 D125 and D139, #3676,
  #3685).
- A 1.0 project's section `specs` and a 1.0 specification's input `schema`
  read the header of the specification each names at that field, as a
  project's `functions` and `codelists` do: a version the engine does not
  read, or another type, fails there as `unsupported_language_version` or
  `unexpected_file_type`, naming the file as `source`, where it failed at the
  named file's own `yamaa` or `type` (SCHEMA-2, #3314).
- A malformed header in the producer a `schema` link names is a finding that
  names that producer as `source` and `entry`, as a finding further into it
  does, and a malformed `yamaa` is located in the producer where it was
  located at the consumer's own `yamaa` (SCHEMA-2, P-ISSUE-1, #3581).
- A raw NUL character in a specification or project file fails with
  `invalid_yaml`; it no longer silently ends the file and drops what follows
  (#3125).
- A 1.0 `columns` entry `copy: {dataset: D, columns: [...]}` declares each
  listed column of the producer that input `D` links through `schema`, with
  the producer's type, label and content metadata and a `Predecessor` origin;
  it expands to ordinary columns before the layers compose, so `resolve()`
  shows them and a later layer overrides or clears one by name (SPEC-9, SUB-20,
  #3030 D19, D70 and D164, #3372).
- A 1.0 structured `source` that holds only `variable` fails as
  `redundant_long_form` at the source, with `shorthand` naming the bare read
  to write instead, which `lint --fix` writes; one that adds a range, filter,
  selection or absence answer keeps its meaning (SCHEMA-15, EXPR-5, #3030
  D217, #3678).

### Layers

- A list written at `parent`, such as `parent: [template.yaml, fragment.yaml]`,
  still fails as `invalid_field_type`, and its `context` now carries the
  `hint` an undeclared `parents` key gives: one parent per file, with the
  layers written as a chain, and a fragment that several files share listed
  under `include` with no parent of its own (LAYER-2, #3614, #3688).
- A `parent` layer whose text is not valid YAML, or not ASCII, fails as an
  entry with that text does, with `invalid_yaml` or `non_ascii_source` at `$`
  and the reader's line and column, located in that parent, instead of
  `engine_rejected` (SCHEMA-3, SPEC-8, #3519).
- `unsupported_language_version` and `unexpected_file_type` at a `parent` or
  `include[i]` name the layer that writes that field as `declaring_source`,
  and `resource_path_not_normalized`, `resource_path_symlink`,
  `resource_path_content_changed` and `resource_path_missing` at a `parent`
  name it as `source`, as they do at an `include[i]`. Each is located in that
  layer, where it was located at the entry's field of that name, or for a
  refused header at the refused layer's own (LAYER-4, FILE-11, P-ISSUE-1,
  #3747).
- In a specification that declares `parent`, a `dependency_cycle` names its
  closed loop in `context.cycle`, such as `[A, B, A]`, as a single-file
  specification's does, instead of every column the cycle leaves unscheduled;
  and an aggregate `derive` binding that reads a later binding reports
  `unknown_derive_variable`, as it does without `parent` (#3134).
- In a specification that declares `parent`, an aggregate whose reducer names
  a variable that none of its `derivations` binds reports
  `unknown_derive_variable` at the aggregate's `expr`, as it does without
  `parent`, instead of `unknown_reference` (LOOKUP-22, #3593).
- A specification read through `parent` reports a bare match value or range
  value that no column takes with its lookup's own refusal, as the same file
  read alone does, where 0.5.0 reported `unknown_reference` (COLUMN-5) for it
  (LAYER-5, LOOKUP-5, LOOKUP-9, #3030 D195, #2934).
- A specification read through `parent` reports a copy cycle through its
  layers' copy entries as its parent does: `producer_workflow_cycle` at the
  same `input.<D>.schema` and with the same `cycle`, where it named the cycle
  from the producer and closed it at the layer's own link (SPEC-9, #3030 D214,
  #3594).
- A layer that overrides its parent's input link to name the parent itself,
  where the parent's copy entry reads that input, refuses the copy as a link
  to the consuming specification (`invalid_producer_contract`,
  `reason: self_reference`), where the copy read the parent's own contract
  (SPEC-9, INPUT-10, #3030 D214, #3594).

### Expressions and verbs

- A `DATE` or `DATETIME` literal written alone in an expression field, as in
  `derivation: "DATE '2025-06-01'"`, returns its date or datetime, where it
  failed with `unsupported_operation` (FORMULA-27, EXPR-4, #3690).
- Expressions gain three numeric functions, each one fixed computation:
  `LOG10(x)`, the base-10 logarithm of the pinned libm; `NORM_CDF(x)`, the
  standard normal distribution function, `0.5 * erfc(-x / SQRT(2))`; and
  `NORM_INV(p)`, its quantile by Wichura's algorithm AS 241. Each takes one
  number and returns a `float`. `LOG10` of zero or a negative number fails as
  `ln_of_nonpositive`, whose context and message now name the function
  (`LN`, `LOG10` or `GEOMEAN`), and `NORM_INV` outside the open interval from
  0 to 1 fails as the new `invalid_probability`, naming the function and the
  value (FORMULA-13, FORMULA-15, #3780).
- `str_case` takes `to: proper`, which writes text as SAS `PROPCASE` does:
  every ASCII letter lowered, then the first character and each character
  directly after a delimiter raised, so `INVESTIGATOR'S DECISION` gives
  `Investigator's Decision` where `title` gives `Investigator'S Decision`.
  The delimiters are the blank, `/`, `-`, `(`, `.` and the tab, or the ASCII
  characters a `delimiters` string lists, each once, matched in the lowered
  text before any character is raised. `delimiters` beside another mode
  fails as `unknown_field`, and an empty list, a repeated
  character or one outside ASCII as `invalid_field_type` (TEXT-5, #3767).
- `duration_text: {source, unit}` writes an `int` or `float` amount of an
  elapsed unit as canonical ISO 8601 duration text, the inverse of
  `duration_value`: days, then hours, minutes and seconds, each zero part
  left out, so 90 minutes is `PT1H30M` and zero is `PT0S`. A source of
  another type fails as `incompatible_input_type`, and a float whose seconds
  leave the binary64 range as `conversion_failed`. It is a recode under
  SUB-19, so a collected `--DUR` keeps its `Collected` origin (TIME-21,
  #3776).
- `str_substr: {source, start, length}` takes the Unicode scalar values of a
  text from position `start`, counted from 1, at most `length` of them or
  every one to the end, and gives missing for a `start` past the end, so a
  long value splits into SDTM's 200-character pieces the same way on every
  host; `str_length: {source}` counts the scalar values as an `int`. Both take
  `missing` and read only text, and a `start` or `length` below one fails as
  `invalid_field_type` (TEXT-13, TEXT-14, TEXT-1, #3775).
- `date_text: {source, forms, invalid}` reads a date written in one of a
  declared, closed list of forms into collected date text, which `impute`
  and `to_date` then read: `iso` passes collected date text through,
  `ddmonyyyy` reads `04MAR2001`, `mdy_slash` or `dmy_slash` reads
  `03/04/2001` month or day first, `yyyymmdd` reads `20010304`, and `monyyyy`
  reads `MAR2001` as `2001-03`. Text in no listed form fails as
  `invalid_date_text` unless `invalid` answers it, and an empty list, a form
  listed twice or both slash forms fail as `invalid_field_type`. It is a
  recode under SUB-19, so the column it derives may keep a `Collected`
  origin (TIME-22, #3769).
- `str_decimal: {source, decimals, width, missing}` writes a number as text
  with exactly `decimals` digits after the point, rounded by the one rounding
  as CSV display precision is, and left-padded with spaces to at least
  `width`, never truncated, as SAS `put(x, w.d)` writes a value that fits; a
  missing source gives `missing`. A text, date or Boolean source fails as
  `incompatible_input_type`, and `decimals` below zero or `width` below one
  as `invalid_field_type`. It rounds, so it is a computed value under SUB-19
  and a `Collected` origin on its column fails (TEXT-15, #3768).

### Lookups and aggregates

- A 1.0 intermediate that drives no row template and declares no `key` fails
  with `missing_required_field` at its `key` before any input is read even
  when nothing reads it, where pruning dropped it and the specification built
  (LOOKUP-3, #3030 D219, #3633).
- A bare `value` in a named intermediate's `between` is an output column
  alone, as it already was in an aggregate's and a structured `source`'s: a
  field of the driver's record that no column takes fails with
  `unknown_field` at `between.value` in every row template, whatever the
  bounds bind, where 0.5.0 read it from the record of the first template's
  driver, or of `base`, and refused it only for the rows of a template over
  another input (LOOKUP-9, NAME-3, #3030 D195, #2934).
- LOOKUP-11 says what the engine already does: a lookup-qualified name reads
  the selected record's column in every `variable` field except a key match
  value, which refuses it with `unknown_field` (LOOKUP-5); derive the value
  into a column and match on the column (#3030 D197, #2934).
- When another intermediate's derivation reads a named intermediate, its bare
  `between.value` is the donor record's field, as a value qualified by the
  donor's dataset is, where 0.5.0 refused it at `between.value` unless the
  driver's record stored the name; a lookup-qualified value reads that
  lookup's column for the donor record (LOOKUP-16, #3030 D199, #3414).
- In such a donor read, a range value, correlated `filter` field or
  derivation field of the intermediate read, or a key value of an
  intermediate its range value reads, that names another input's record
  fails with `unknown_field` (LOOKUP-16) at the reading derivation, naming
  the read, the reading intermediate and the intermediate it reads, where
  0.5.0 could read another record's value or fail with `engine_rejected`
  (`result_projection`) (#3030 D199, #3414).
- A named intermediate's `between.value` qualified by an intermediate that
  builds a row reading it fails with `unsupported_operation`
  (`intermediate_driver_range_value`) at `between.value`, and for rows
  another input builds with `missing_required_field` at that row driver's
  `key` (LOOKUP-3), where 0.5.0 looked the driving intermediate up by a key
  it does not declare (LOOKUP-9, #3030 D199, #3414).
- A qualified aggregate's written `key` reports its refusals at the key, as a
  named intermediate's does: a key column the relation does not have, and a
  pair whose types cannot compare, at `key`, and a match value that reads no
  value of the row at its pair, `key.<column>`, where 0.5.0 reported each at
  the aggregate's `expr` or `filter`; a missing key column no longer hides
  its pair's refused match value (LOOKUP-5, #3030 D196, #2934).
- The run report counts an absence that a named intermediate answers,
  declared or by default, in an `absent` handler row at the read's path, as
  it counts an implicit join's, where 0.5.0 wrote `no_match`; `str_extract`'s
  `no_match` keeps its name (LOOKUP-14, COLUMN-14, #3030 D58 and D202,
  #3589).
- In the run report, an `absent` handler row's `RULE` cites LOOKUP-24, which
  states what answers a lookup without a candidate, where 0.5.0 cited NAME-3
  (CHECK-24, #3030 D204, #3610).
- A named intermediate selects by distance with
  `nearest: {source, to, unit}`: the candidate whose date or datetime
  `source` lies nearest `to`, a value of the current row read as a key match
  value is, counted in `unit` as `diff` counts it, a tie going to the
  earlier `source`, then to stored order, and a candidate without a distance
  never chosen. Beside `order_by` or `keep` it fails as
  `prohibited_construct` (LOOKUP-26, #3030 D206, #3693).
- A named intermediate that writes `inner_join` is a pair relation: one
  record for each matching pair of its `dataset`, the left side, and its
  `inner_join`, the right side, matched on its required `key`, in left then
  right stored order, where `order_by` with `keep` on a partner read one of
  several and dropped the rest. Its required `derivations` are its fields,
  read from both sides, and it is read as an input is: a row template drives
  on it, a named intermediate looks it up and a qualified aggregate with `key`
  reduces it. Beside `between`, `order_by`, `keep`, `nearest`, `absent` or
  `require_match`, or with `SELF` as a side, it fails as
  `prohibited_construct` (LOOKUP-27, ROW-2, ROW-7, #3673 D263, #3786).
  Its global materialization requires the whole-table fallback under either
  partition mode, and its physical input is admitted whole before the join.
- `aggregate` reduces with `STR_JOIN(x)`, which joins a group's non-missing
  values into one text, each written as a `str` column writes it, in the
  order of the aggregate's new `order_by`, ties in stored order, with its new
  `separator` between two values, and gives missing when no value is present.
  The new `distinct: true` writes each text once, and makes `COUNT(x)` count
  each different value once. `STR_JOIN` without `order_by` or `separator`,
  either field beside another expression, and `distinct` beside anything but
  a bare `STR_JOIN(x)` or `COUNT(x)` fail as `unpaired_fields` (LOOKUP-10),
  and arithmetic over `STR_JOIN` as `incompatible_input_type` (FORMULA-18,
  FORMULA-23, #3774).
- `aggregate` reduces with the statistical reducers, each with one named
  definition: `MEDIAN(x)`, `Q1(x)`, `Q3(x)` and `QUANTILE(x)`, R's default
  quantile (type 7 of Hyndman and Fan) at 0.5, 0.25, 0.75 and at the
  aggregate's new `quantile`; `STDDEV(x)` and `VARIANCE(x)`, the sample
  deviation and variance with divisor n - 1; and `GEOMEAN(x)`, the `EXP` of
  the mean `LN`. Each skips missing values and returns a `float`, missing for
  a group with no value and, for `STDDEV` and `VARIANCE`, with one. `MEDIAN`
  is no longer refused as `prohibited_function`. `QUANTILE` without
  `quantile`, or `quantile` beside another expression, fails as
  `unpaired_fields` (LOOKUP-10), a `quantile` outside 0 through 1 as
  `invalid_field_type`, a non-numeric argument as `incompatible_input_type`
  and a zero or negative `GEOMEAN` value as `ln_of_nonpositive` (FORMULA-15,
  FORMULA-18, FORMULA-19, FORMULA-23, FORMULA-24, #3779).

### Row templates

- A structured `source` reads its `between` value as any other read of its
  derivation, as it already did inside a `case`: a row template whose
  `source` names a column with a row-local column-level derivation, such as
  `ASTDT` derived from `AE.ASTDT`, completes that column in its row phase,
  where 0.5.0 refused the specification with `phase_boundary` at
  `between.value`; and a column-level `source` whose `between` value reads a
  column that is not row local, such as an aggregate, is not row local
  either, so a `rows` entry that names its column fails with
  `duplicate_derivation` (SPEC-6, #3030 D118, #3253).
- A column-level derivation that holds an aggregate in a `case` result is not
  row local, as one that is an aggregate or holds a window already was: a
  `rows` entry that names its column fails with `duplicate_derivation`
  (SPEC-6), where 0.5.0 let the entry's own derivation replace it, and a row
  template that reads the column fails with `phase_boundary` at the read
  (COLUMN-4), where 0.5.0 completed the default in the template's own scope,
  failing with `invalid_aggregate_context` in an ungrouped template and
  reducing over each group in a grouped one (#3030 D132, #3344).

### Checks

- `not_missing` takes `when`, so it checks only the rows whose `when` is
  true, and `max_fraction`, so it passes while the checked rows that lack a
  value are at most that share of the checked rows, compared as a
  `row_count` share is and zero when no row is checked. A share outside 0
  through 1 fails as `invalid_declaration`, and a name in `when` that is no
  column as `unknown_field`. A failure stays `not_missing_failed`, with
  `denominator` under `max_fraction` (CHECK-5, CHECK-4, CHECK-24, #3030 D208
  and D209, #3687).
- An intermediate's `unique` takes `severity: warning` when the intermediate
  declares `keep` and `order_by`, or `nearest` (#3693): a repeated combination
  fails nothing, every read still selects by them, and the check is a
  run-report row, first among the check rows, so the specification declares
  `output.report`. Elsewhere `warning` fails as `value_not_permitted`
  (LOOKUP-17, CHECK-23, CHECK-24, #3030 D210 and D211, #3687).

- A project run or submission that selects a section the project does not
  declare, or a name other than `sdtm`, `adam` or `send`, is refused in every
  host and on the command line with the new validation condition
  `unknown_section`, naming the requested section and the sections the project
  declares, before any specification builds; before, an unknown name was
  `engine_rejected`, a run of an undeclared section built nothing, and a
  submission of one reported `missing_required_field` (PROJECT-14, #3030 D73,
  D98 and D126, #3335).
- Refused `parents`, the retired `date_*` and `datetime_*` verbs and removed
  formula functions name their replacement in `context.hint`; a non-empty
  retired parent list no longer causes missing-root-field findings alongside
  its `unknown_field` finding (#3213).
- `engine_rejected` names the step of the operation that refused in the
  context key `step`, not `stage`, and its message reads `the engine refused
  the operation in its <step> step: <code>`, so "phase" and "stage" keep
  their one meaning each (COLUMN-16, #3030 D71, P-PHASE-1, #3413).
- A Define submission that refuses a published dataset's format as
  `unsupported_operation` names the format in `context.operation`, as every
  such refusal does, instead of `context.detail` (COLUMN-15, #3030 D95, #3146).
- `artifact_outside_document` names the dataset, the artifact's `output.path`
  and the Define-XML document's path, each as written, in `context.dataset`,
  `context.artifact` and `context.define`, and its message names all three,
  where its context held only a fixed `detail` (DEFINE-16, #3603).
- Define publication's engine refusals carry a `stage` and a closed `code` in
  their `context`: an output or table bound reports `define` with
  `output_limit` or `resource_limit` and its `resource`, `limit` and `actual`
  alongside the existing `detail` text, a transport value the writer cannot
  represent reports `output_projection`, and a refused Define target adds the
  `code` of its cause, such as `invalid_target` (#3145).
- A `duplicate_derivation` that refuses a `rows` entry naming a column whose
  column-level derivation reads a `SELF` intermediate gives
  `not_row_local: self_intermediate` in its `context` instead of
  `named_intermediate`: a read of an input-backed named intermediate is row
  local (SPEC-6, #3030 D71 and D166, #3344).
- An `odm` read under a derivation that declares `unconvertible` is named at
  its operation's path, such as `columns.AGE.derivation.odm.item`, as building
  already names it, instead of `columns.AGE.derivation.value.odm.item`
  (#3136, #3225).
- A structured `source`'s `incomparable_range_types` names the binding's
  `variable` in its `context`, as each other refusal of its range does
  (LOOKUP-9, #3030 D199, #3414).
- Without `rows`, a key column whose derivation reads a non-key column
  reports `key_dependency` at its derivation whatever the operation, so a 1.0
  formula reports it at `columns.<C>.derivation`, as a 0.5 `compute` does,
  instead of at the column (COLUMN-7, #3030 D18, #3651).
- A 1.0 column without `name`, or a row template or intermediate without
  `id`, fails as `missing_required_field` at `<collection>[i].<identity>` in
  the layer that writes it, where it failed as `engine_rejected`; a `copy`
  entry, which carries no `name`, needs its `dataset` and `columns` where it
  is written (LAYER-4, SCHEMA-13, SPEC-9, #3030 D73, #3678).
- A `str_contains` pattern that is not a string literal, as in
  `str_contains(AETERM, PATTERN)`, fails with `invalid_expression` under
  FORMULA-8, which states that failure, where it cited FORMULA-1 (#3690).
- In `aggregate.expr`, arithmetic over a reduction or a grouping column that
  is not numeric, such as `MIN(AE.AESEV) + 1`, fails with
  `incompatible_input_type` under FORMULA-23, from the declared types and
  before any record is read. It failed under FORMULA-12, and over a reduction
  only once a group was evaluated (#3690).
- `invalid_function_argument` names the `argument` of every fault of one
  argument: an integer outside the 64-bit range, an invalid `DATE` or
  `DATETIME` literal and a value that is no scalar also give the text it is
  written as in `context.value`, null for no scalar text; and a refusal at run
  time spells its keys as preparation does, `argument`, `expected_type` and
  `actual_type`, where it wrote `parameter`, `expected` and `actual` (FUNC-5,
  #3924).

### Files and paths

- A specification or project path a caller passes that reaches no entry, a
  directory or another entry that is not a regular file, or a link fails with
  `resource_path_missing`, `resource_path_not_regular_file` or
  `resource_path_symlink` at no field, naming the path as given, on every
  route and in every host, as the command line and `lint()` report it; a
  specification path was `engine_rejected`, and a project path
  `project_environment_missing` or `project_environment_invalid`. A
  specification a project lists that the walk cannot reach fails the same
  way at its listing, such as `sdtm.specs[0]`, naming the path as written,
  where it was `engine_rejected` (FILE-1, FILE-7, FILE-8, FILE-11, #3030
  D107 and D188, #3321).
- A `parent` written with a backslash, an empty segment or a trailing
  separator, such as `std//base.yaml`, `base.yaml/` or
  `//server/share/base.yaml`, fails validation with
  `resource_path_not_normalized` at `parent`, naming the path as written,
  instead of `engine_rejected` (FILE-5, LAYER-2, #3201).
- A `parent` that reaches a symbolic link, junction or other reparse point,
  as its own name or a directory on its way, and a mapping `dict` file that
  does, fail validation with `resource_path_symlink` at that field, naming the
  path as written, instead of `engine_rejected` (FILE-8, LAYER-2, #3226).
- Windows network shares (UNC paths) and mapped drives are admitted for
  specifications, projects, inputs, outputs and `read_odm`; symbolic links,
  junctions and other reparse points stay refused (#3030 D15, #3147).
- `read_odm` refuses a source file that is a symbolic link, as every other
  input does (#3147).
- On a network share, a link is refused where the file server reports it as
  one, as Windows servers do; a parent on a share the entry is not on is
  refused when it declares relative input or output paths; and saves from two
  computers into one share folder are not serialized (#3177).
- A parent specification on another drive than the entry reads its relative
  inputs beside itself instead of failing (#3177).
- Two names that reach one file read the same bytes (FILE-9): a file
  rewritten between the captures of two of its hard links fails with
  `resource_path_content_changed`, where 0.5.0 read both versions (#3177).
- A file rewritten between the captures of two of its hard links also fails
  with `resource_path_content_changed` when the name read first was renamed
  or removed in between. A new file to which the file system gives a removed
  file's identity during a run fails the same way when its bytes differ
  (FILE-9, #3201).
- A file that changes before a submission's composition is verified fails
  with `resource_path_content_changed` at the field that declared it through
  any resolver, where a caller's resolver whose references are not the files'
  locations, such as the memory resolver, reported `engine_rejected`
  (FILE-10, #3686).
- A file that changes or disappears after a specification's preparation read
  it, before the preparation verifies what it read, fails at the field that
  declared it with `resource_path_content_changed` or `resource_path_missing`,
  where it reported `engine_rejected` (FILE-7, FILE-10, #3686).

### Saving

- `save()` returns the absolute paths it wrote, with forward slashes, in
  publication order: a list of `str` in Python and a character vector,
  returned invisibly, in R. A refused save's `yamaa.Error`, and in R the
  `yamaa_error` condition, carries `paths`, the files it wrote first, such as
  a failed run's report (#3030 D38 and D69, #3247).
- A save stages every file of every specification or section before it
  replaces any target: a file that cannot be staged, or a later section's
  target that can no longer be written, stops the save with nothing written,
  where 0.5.0 wrote the files before it (#3030 D99, #3247).
- On Linux and macOS a saved file is created with mode 0666 less the umask,
  as other tools create files, and a file that replaces an existing one keeps
  that file's permission bits; 0.5.0 saved every file readable by its owner
  only (#3030 D92, #3267).
- A save into a directory that does not exist, onto a directory or through a
  symbolic link fails with `resource_path_missing`,
  `resource_path_not_regular_file` or `resource_path_symlink` in the `output`
  phase, at the field that declares the file and naming it as written (for
  a table saved to a path the caller gives, at no field and as given),
  instead of `engine_rejected` with code `invalid_target` (FILE-7, FILE-8,
  FILE-11, #3030 D189, #3321).

### Lint

- `yamaa.lint(paths, fix=False)` and `yamaa_lint(paths, fix = FALSE)` check
  specification files against the style guide in Rust and return one row per
  finding, with the columns `file`, `line`, `column`, `finding`, `spec_path`
  and `message`; with `fix`, the layout fixes the lint proves safe are applied
  first (#3030 D40, #3176).
- `python -m yamaa.style` and the Python package's `style` extra are removed:
  lint with `lint()`. A suppression comment is spelled
  `# yamaa-lint: allow <finding> -- <reason>`, and `literal_form` is no longer
  reported (#3176).
- A specification is linted by the field orders of the 1.0 schema: its
  header (`yamaa`, `type`, `model`) and the fields up to
  `filter`, `clear` among them, may stand together before `output`, and
  `model`, `clear`, an input's `byte_order_mark` and `key` and an
  intermediate's `absent` have their places. Directory discovery requires
  the 1.0 header and skips files declaring `schema_version` (#3326, #3443).
- A directory expands to every 1.0 file type, and a project, codelists or
  function file is linted by its own schema: every mapping its classes
  describe is in field order, the header stands together, one blank line
  precedes each submission section of a project file, a function file's
  `tests` and a codelists file's `codelists`, and the entries of those two
  lists are spaced like specification columns (#3030 D179, #3407).
- A finding in a 1.0 file names its spec path in the notation of the issues
  table: a list entry that writes `name` or `id` is named by it
  (`columns.AGE`, `rows.first`), and a key that is not a bare segment is
  quoted (#3030 D179, #3407).
- In a 1.0 specification `repeated_row_derivation` reads row locality as
  SPEC-6 states it, so a read of an intermediate an input backs may move to
  column level and only a `SELF` intermediate, an aggregate or a window keeps
  a derivation in its templates; across drivers quoted text, a YAML number
  and null are literals. `redundant_intermediate` compares an intermediate's
  `key` with its input's declared `key` and reads `absent` (#3407).
- The lint reports three canonical spellings of a 1.0 file, which `fix`
  rewrites: `restated_default` (a field or handler that writes its default),
  `scalar_as_text` (grammar text such as `"0"` or `"NULL"` in an expression
  field) and `redundant_long_form` (the long form validation refuses as
  SCHEMA-15). A rewrite is kept only when the file reads as its values with
  exactly that change (#3030 D182, P-HND-3, P-KIND-1, P-LONG-1, #3408).
- The lint reports `unused_input_key`, an input's declared `key` that no
  implicit join or keyless aggregate reads, and `equality_filter`, a lookup
  filter conjunct that compares a donor field with a current-row value, which
  `key` states as a pair; neither has a fix (#3030 D184, P-JOIN-1, P-ORD-3,
  #3409).
- The lint reports `partial_restatement`, a layer that restates a mapping it
  inherits, writing it empty or writing again an entry exactly as it inherits
  it, and leaves out entries that then come back from its parent, which the
  message names. It reads the layers the file inherits and includes, and it
  has no fix: clearing the mapping replaces it and writing only what the
  layer changes keeps the parent's entries, and either may be intended
  (#3689). A layer, a file that declares `parent` or `include` or a fragment
  that a specification of the same call includes, itself or through its
  parent chain, is not read for `restated_default`, `unused_input_key` or
  `missing_label`, since a value it writes may replace one it inherits
  (#3688).

### Command line

- A `yamaa` command-line binary is built from the new `yamaa-cli` crate:
  `yamaa --version` prints the engine version, the language versions it
  reads, its optional features, the host `cli` and the platform, from the
  Rust facade's new `yamaa::info()`, or with `--format json` the same as one
  object. `check`, `run`, `submission` and `resolve` read the type their
  PATH declares in its `type:` header: a spec is checked, run or resolved
  alone, and a project is checked or run whole, one specification with
  `--spec NAME` or one section with `run --section`, or composed by
  `submission`. They and `lint` print the facade's summaries, issue lines and
  error text, or with `--format json` one canonical JSON document, and
  `resolve` prints the resolved specification as canonical JSON in both
  formats; `run` and `submission` save and print the paths written. A
  project run's JSON `members` lists every member, one whose listing cannot
  be read under the path the project file writes, and a submission's JSON
  `created` holds the time its documents carry, which it also prints when
  `--created` is omitted. They exit 0; 1 for findings or a refusal, such as
  an unknown section or a PATH that cannot be read, declares a `type` that
  names no file type, or is written in language version 0.5
  (`unsupported_language_version`); and 2 for a PATH whose type the command
  does not take, such as a spec given `--spec` or `--section`. The binary's
  engine claims no host language, so it reads no project's `environments`
  entry and refuses a run that calls a project function. `yamaa selftest`
  runs the selftest cases as the hosts' `selftest()` does and prints the
  same report with the host `cli`: `yamaa selftest: succeeded, 5 of 5 cases
  passed`, then the engine, language, host and platform. With `--format json`
  it prints the report's `status`, `cases` and `info`, and it exits 0 unless
  a case failed. `yamaa read-odm SOURCE OUT` reads an ODM XML file, or a
  member of a TAR archive, as the hosts'
  `read_odm()` does, with the same options, saves the clinical items to OUT
  as CSV or Parquet, as its extension `.csv` or `.parquet` selects, and
  prints the path written, or with `--format json` the source, the number of
  items and the path. Another extension is refused as
  `unknown_artifact_profile` before anything is written, and that refusal,
  like one of SOURCE, exits 1. The JSON `status` of `read-odm` follows the
  read, as `run`'s follows the run: once the items are read it is
  `succeeded`, even when the save is then refused, which its `issues`
  report, and only a refused read is `failed`. `yamaa schema TYPE` prints
  the JSON Schema of a file type as the hosts' `schema()` returns it, then
  one line feed, in both formats, and any other TYPE is refused with
  `unexpected_file_type` and exits 1, its JSON echoing TYPE as `type` (#3030
  D12, D41, D68, D97 to D99, D103, D108, D110, D119, D122, D123, D125, D129,
  D130, D134, D149, D169, #3060, #3062).
- Ctrl+C stops `check`, `run` and `submission` at the engine's next
  cancellation checkpoint, so they print nothing and a save writes every file
  it planned or none; the other commands stop at once, so an interrupted
  `lint --fix`, which replaces each file atomically, can leave some files
  fixed and others not. The process then ends the native way rather than with
  exit status 0, 1 or 2: on POSIX it re-raises SIGINT, which shells report as
  status 130, and on Windows it exits with `STATUS_CONTROL_C_EXIT` (#3030 D46,
  D74, D203, #3415).
- A run that calls a project function on an engine without project
  functions, the command line's or a Rust embedder's that supplies none, is
  refused as `unsupported_operation` at the first derivation that calls one,
  such as `columns.<C>.derivation`, so the issue gives that specification's
  file, line and column. The first is in the order a formatted file writes
  derivations: the intermediates', then the columns', then the row templates'
  (#3030 D221, #3677).

### Packages

- `spec.run(stream=True)` in Python and `spec$run(stream = TRUE)` in R build
  a dataset as its output is read, one batch per pull of an Arrow stream: a
  `yamaa.Table` in Python, and in R an Arrow C stream of class
  `nanoarrow_array_stream`; releasing the stream before its last batch cancels
  the run (#3697).
- `yamaa.selftest()` and `yamaa_selftest()` run the selftest cases that every
  package carries, benchmarks with their independently authored expected
  files, through the installed engine and compare each result with its
  expected files, writing no file and using no network. The result has
  `status`, `cases` (one row per case: `case`, `status` and `message`) and
  `info` (the engine version, language versions, features, host, host
  version and platform), and printing it gives the report, the same words in
  both hosts: `yamaa selftest: succeeded, 5 of 5 cases passed`, then the
  engine, language, host and platform. Each adapter, the ODM XML reader
  included, has a case, so a shipped package prints no `not covered:` line
  (#3030 D28, D105, D108, D119, #3062, #3378).
- `yamaa.schema(file_type)` and `yamaa_schema(file_type)` return the JSON
  Schema of a file type, `spec`, `project`, `codelists` or `function`, as
  canonical JSON text: the document committed in `yaml/json/`, which the
  engine embeds, so an editor can validate and complete yamaa files as they
  are typed. Any other type raises `yamaa.Error` (`yamaa_error` in R) with the
  issue `unexpected_file_type` (SCHEMA-2); the Rust facade gives the same as
  `yamaa::schema` (#3030 section 2.12, D149, #3331).
- `yamaa.conditions()` and `yamaa_conditions()` return the condition
  catalogue, one row per condition: its `condition`, `severity`, `phases`,
  `rules`, `message` template, `renamed_from` and `retired_in`: each of the
  four conditions that 1.0.0 renames names its 0.5 name, and each of the
  seven that it retires keeps a row with the release that retired it.
  `yamaa conditions` prints it, as a table or with `--format json` as
  objects, and the Rust facade gives it as `yamaa::conditions`;
  `yaml/conditions.yaml` at a release's tag holds the same catalogue (#3546,
  #3700).
- The Python package has no runtime dependencies: Polars leaves them for the
  `test` extra, which also takes pandas for `to_pandas()` (#3030 D11, #3402,
  #3403).
- The Python package no longer depends on packaging: the engine reads a
  function's uv lock and compares versions itself, as packaging 26 compares
  them, with the findings the Python host reported, and the Rust facade
  offers the comparison as `verify_uv_lock` (FUNC-3, #3030 D8, D11, D172,
  #3399).
- A package whose native module does not match its Python or R code refuses
  to load, with a message that names both interface versions: `import yamaa`
  raises `yamaa.InterfaceError`, an `ImportError` that carries the refusal's
  fields, and `library(yamaa)` stops with the message (#2870, #3679).
- Both hosts refuse a call into a result that another call is still using
  with one message that names the result in words, such as
  `project run handle is in use or poisoned`. Python said
  `project handle is in use or poisoned` for a project run or a
  submission, and R said, for example, `project run handle in use` (#3702).
- Both packages still build the shared engine into their native module and
  call it through its Rust facade, as 0.5.0 did; the internal engine C ABI
  that #2870 designed does not ship (#3673 D281, #3877).
- The engine's own tables are columnar, and Arrow is only their form at the
  hosts' edge, Parquet's and the Rust facade's: a build without the facade's
  `arrow` and `parquet` features links no Arrow crate, and one without
  `parquet` links no Arrow IPC or FlatBuffers. Every package builds both, so
  it links the same crates (#3696).
- The Python source archive builds offline: it carries the crates.io crates
  that its lock selects and only the engine, boundary and Python binding
  crates, without tests, examples or a toolchain file (#3030 D55, #3105).
- The R source package builds from the same kind of bundle, with only the
  engine, boundary and R binding crates and their trimmed lock, and neither
  source archive carries a toolchain file anywhere, its vendored crates
  included, so an offline installation never makes rustup select or download
  another toolchain (#3030 D55, #3105).
- Installing the R package ignores a Cargo build directory and a rustc
  wrapper, such as a compiler cache, that the environment or a
  `.cargo/config.toml` in a parent directory sets, so the build writes only
  inside the package, as CRAN's Repository Policy asks (#3030 D86, #3255).
- On Windows with Cargo 1.91 or later, the R package installs from source
  from a path that contains `{` or `}`, such as R's temporary directory:
  Cargo reads the build directory that the installation sets as a template,
  so the installation sets it relative to the package (#3275).
- The installed R package no longer carries the inputs of its tests: they
  move from `inst/` to the source package's `tests/`, which `R CMD check`
  reads and R does not install, so an installation is about 8 MB smaller
  (#3105).
- The Python wheels' native module no longer carries its symbol table, about
  4.5 MB of its 20.6 MB on Linux, so a Rust backtrace from a wheel names no
  functions. The R package strips nothing itself, as CRAN's Repository Policy
  asks, so its shared object keeps its symbols on Linux and macOS; on Windows,
  R's own toolchain links every package DLL with `-s`, so `yamaa.dll` carries
  no symbol table there (#3106, #3030 D140, #3292).
- The R source package's `src/rust/Cargo.toml` leaves out the `dist` profile
  that only the wheels and the command-line binaries build with, so it
  names no stripping (#3120).
- Every package ships `COMPONENTS.tsv` beside its third-party notices: an
  inventory, without digests, of the components that it is built from, with
  each one's version, license, source and purpose. A wheel's also names the
  Rust standard library of the pinned toolchain that builds it, which a
  source archive's leaves out. An installed R package's names the standard
  library that it linked: the R package's `configure` adds that row with the
  version that `rustc` reports, so the R binary packages name the pinned
  toolchain's (#3120).
- Each package's `LICENSE-THIRD-PARTY.txt` lists only the crates of its own
  binding: the R package's no longer names pyo3's crates, nor the Python
  packages' extendr's (#3120).
- The third-party notices list only the crates that a package links on the
  supported targets, about 60 fewer than before, and no longer copy the
  standard library notice's crates for other targets and the compiler's
  tools. The notices, `COMPONENTS.tsv` and R's `inst/AUTHORS` name the one
  license that yamaa relies on for each component, such as `BSD-3-Clause`
  for zstd, never the GNU licenses that some crates also offer. No package
  text names a GNU license, apart from the LLVM exception's GPLv2 clause and
  the upstream files of a few vendored crates in the source packages, and the
  release checks enforce it (#3364).
- The source packages no longer carry zstd's GPL-2.0 text, which yamaa does
  not rely on, and each vendored crate that no supported target compiles, such
  as `r-efi` and the WebAssembly and WASI crates, keeps only its manifest, so
  the R source package is about 0.9 MB smaller and the Python source archive
  about 1.9 MB (#3368).
- The command line's `COMPONENTS.tsv` names musl, which its executables for
  the two musl targets link statically, with its version and license (#3493).
- The notices' standard library section names `compiler_builtins`, which
  every package links, under MIT AND Apache-2.0 WITH LLVM-exception, with its
  license texts, where the Rust project's notice gives it only Apache-2.0 OR
  MIT (#3494).
- The wheels' License-Expression adds `Apache-2.0 WITH LLVM-exception`, for
  the standard library's `compiler_builtins`, so the metadata that PyPI shows
  covers everything that a wheel links (#3030 D185).
- The notices' standard library section names every third-party crate that
  the Rust standard library links, from the toolchain's sources: it adds
  `addr2line`, `adler2`, `miniz_oxide` and `object`, which the Rust project's
  notice leaves out, and names `memchr` at the version that `std` links. The
  Linux command-line archives also carry `LICENSE-MUSL.txt`, the notice of
  the musl C library that their static binaries link (#3369).
- Each package's third-party notices follow the features that its build
  enables, so they drop `aho-corasick`, `const-random`, `equivalent`,
  `indexmap`, `toml_writer` and `hashbrown` 0.16.1, which no build compiles,

- The engine builds one release each of lz4_flex, zstd, base64 and
  num-bigint, the ones that Parquet 55.2.0 uses, where it built two, so every

  and num-bigint 0.5.1 (#3696).

  downloaded `yamaa.exe`, and **More info**, then **Run anyway**, starts it
  (#3030 D12, D49, D52, #3060).
- 1.0.0 carries `yamaa-1.0.0-conformance.zip`, and each later release its
  own: the language's conformance files as committed at its tag. They are the
  closed grammars of expressions and string templates,
  `yaml/grammar/expression.yaml` and `yaml/grammar/string-template.yaml`, with
  their parse vectors and `yaml/grammar/README.md`, which states their file
  format and shape notation; the evaluation set of the expression language,
  `yaml/conformance/expressions.yaml`, whose cases give the value an
  expression takes over a small table, or the issue it reports; and the
  project's `LICENSE`. The engine reproduces every case, and another
  implementation can check itself against the same files (#3545, #3690).
- A Linux machine whose packaged Rust is older than 1.82 builds either source
  archive by the offline toolchain route: Rust's standalone installer, carried
  in and installed with no rustup or network, which native qualification runs
  on Linux x86_64 and aarch64. The new guide
  [Installing in a restricted environment](https://elong0527.github.io/yamaa/articles/restricted-environments/)
  gives its steps, with those for internal mirrors and carried-in files
  (#3030 D54, #3107).
- R source builds are supported on Linux aarch64, with R 4.6.1: native
  qualification builds and installs the R source package there with the
  network disabled and runs the conformance corpus with it. No
  `R CMD check --as-cran` runs on aarch64, and no lane there uses R 4.2
  (#3030 D49, #3061).

### Rust facade

- The facade keeps the 1.0 use cases and removes its pre-1.0 entry points:
  `Engine::check`, `Engine::build`, `Engine::compile` and
  `Engine::resolve_specification`, with `Request`, `Build`, `Plan`,
  `RunRequest`, `AttemptFailure`, `SourceBytes` and `ResolvedSpecification`;
  `Progress` and the `observe` module's events, with
  `EngineOptions::observer`; the path-based free `read_odm`; and
  `style_same_value`. `SpecRequest::check`, `SpecRequest::run`,
  `SpecRequest::resolve` and `Engine::read_odm` take their place, a `Plans`
  holder still keeps a host's compiled plans, and `Run::build` gives way to
  the qualification-only `Run::observations` (#3030 D22, D72, D192, #3415).
- `Engine::spec(path)` returns a `SpecRequest` and `Engine::project(path)`
  a `ProjectRequest`, which hold a path as a host's lazy object does:
  `project`, `section`, `reusing` and `cancel_with` add the project file, the
  section, the `Plans` holder and the token, and `check`, `check_on`, `run`,
  `stream`, `resolve`, `names`, `spec` and `submission` replace
  `Engine::spec_check`, `spec_check_on`, `spec_run`, `spec_run_reusing`,
  `spec_stream`, `spec_resolve`, `project_spec`, `project_names`,
  `project_check`, `project_run`, `project_run_reusing` and
  `project_submission`, whose creation time and source-system version a
  `SubmissionOptions` carries. A request given no holder runs through an
  empty one, and one given no token polls a token that nothing cancels
  (#3765).
- `Failure` is the one error of every facade operation, and `Error` is removed:
  a failure's `kind`, a `FailureKind`, is `Rejected` with its issues, or
  `Cancelled`, `Table`, `Unavailable`, `Internal` or `Stream`, which carry what
  those `Error` variants carried, and its message is the hosts' error text, as
  `Failure::from_error`, now removed, made it. `Error::Host` and
  `Error::Resolver`, which no operation returned, have no kind: a failed
  project function or resolver is an issue of the result. `Diagnostic::phase`
  is a `Phase`, an enum of the twelve phases, and `Diagnostic::code` a
  `ConditionCode`, which only a condition the registry holds parses into; so
  are the catalogue's `Condition::phases` and `Condition::condition` (#3765).
- The crate root re-exports only what configures an engine or comes back
  from one, and the two host ports move under `yamaa::host`:
  `host::functions` holds the project-function port with `FunctionError`,
  `CallError`, `HostPayload`, the lock types, `decode_renv_lock` and
  `verify_uv_lock`, and `host::resolver` the resolver port with its requests,
  replies, kinds and `ResolverFailure`. The root keeps `ProjectFunctions`,
  `HostLanguage`, `ResourceResolver` and `MemoryResolver`, and `Scalar`,
  `ScalarRef`, `Date` and `DateTime` stay in `yamaa::scalar` alone.
  `EncodedScalar`, `ScalarDecodeError`, `ContextValue::Uint` (an integer
  above `i64::MAX` is a `Wide` spelling), the public `text::Action`, `Report`
  (`diagnostic::issues` builds the issues table) and `Summary`'s public
  fields (`lines()` gives them) are removed, and `Run::observations` takes no
  flag, with `Run::measured_observations` beside it (#3766).
- `SpecRequest::check` and `ProjectRequest::check` return a `Check`, whose
  `issues()` is the former table, and `Check`, `Run`, `ProjectRun` and
  `Submission` report `status()`: `succeeded`, `failed`, or `skipped` for a
  project-run member whose producer did not complete (#3030 D36, #3148).
- `Run::save`, `ProjectRun::save` and `Submission::save` return the paths
  written, `Failure` carries `paths`, and `SaveOutcome` is removed (#3247).
- Every result renders its printed text as a `Summary` (`summary()`), and
  `Diagnostic::text()` and `to_value()` give an issue's printed line and JSON
  object; `lint()` returns a `Lint` with its table, the files it linted and
  rewrote, and its summary line, and a `Failure`'s message names the call
  that refused (#3030 D37, D39, #3248).
- `Diagnostic` carries `message`, rendered in Rust from the template that
  `yaml/conditions.yaml` registers for its condition, the same text in every
  host; the issues table gains it with the other columns of #3030 D28 (P-MSG-1,
  #3030 D95, #3146).
- `Table::preview()` renders a table's printed preview: the header
  `yamaa.Table: <r> rows x <c> columns`, a row of names, a row of types
  (`list<str>` for a list column) and at most 10 rows, the first 5, `...` and
  the last 5, of the first 8 columns, each cell cut at 20 characters (#3030
  D43, D167, #3400).
- `Engine::file_type(path)` returns the `FileType` a file declares (`Spec`,
  `Project`, `Codelists` or `Function`), read from its `yamaa` and `type`
  header once through the engine's resolver; the command line dispatches on
  it. A file that declares `schema_version` has no type and is refused as
  `unsupported_language_version` at `schema_version`, naming language version
  0.5, and a path that reaches no regular file as `resource_path_missing`,
  `resource_path_not_regular_file` or `resource_path_symlink`, naming the path
  as given (SCHEMA-2, FILE-7, FILE-8, #3030 D122, D125, #3328).
- `Submission::created()` gives the creation time the documents carry, and
  `ProjectRun::members()` gives every member in run order with the name its
  member line prints. A member whose listing could not be read is named by
  the path the project file lists, where its line printed the resolved
  location of a missing file (#3030 D69, D129, D130, #3329).
- `yamaa::SECTIONS` lists the sections a project file declares, `sdtm`,
  `adam` and `send`, in run order: the `section` that
  `ProjectRequest::section` takes (#3434).
- `SpecRequest::check_on(parent)` checks a fragment composed on the
  specification `parent` names, reading `parent` as a caller path, and
  refuses a specification that declares `parent` or `include` with a
  `FailureKind::Rejected` failure (LAYER-4, FILE-1, #3694, #3765).
- An engine without project functions builds every specification that calls
  none, with or without a project file, where it refused every build with a
  project; a build that calls one is still refused as `unsupported_operation`
  (#3030 D110, #3249).
- `EngineOptions::neutral` configures an engine that claims no host language,
  for the command line and a bare Rust embedder, and `EngineOptions::default()`
  is now one: it reads no project's `environments.<host>` entry, so it
  verifies no lock and activates nothing. It checks and resolves a
  specification that calls a 1.0 project's function and refuses to run it as
  `unsupported_operation` (#3030 section 2.10, D123, #3324).
- `HostLanguage` no longer implements `Default`: a host names its language
  with `EngineOptions::new`, and an engine that claims none uses
  `EngineOptions::neutral` (#3030 D123, #3355).
- An embedder's `ResolverFailure::from_code("directory" | "file" | "other" |
  "unreadable")` now raises the file-rule conditions instead of `rejected`
  (#3147).
- `Engine::read_odm` through a resolver reports a source over the 10 GiB
  per-file source bound as `source_odm_limit_exceeded` with the reason
  `ODM source exceeds 10737418240 bytes`, instead of as an ODM XML size; such
  a source is held whole before `max_expanded_bytes` applies (#3201, #3375).
- `Error::Odm` and `OdmError` are removed: `Engine::read_odm` refuses with
  a `FailureKind::Rejected` failure and its one issue (#3030 D158, #3375).
- `Engine::define`, `DefineRequest`, `DefineBuild` and `DefineArtifact` are
  removed. `ProjectRequest::submission` composes Define-XML and refuses a
  section the project does not declare, or a name other than `sdtm`, `adam`
  or `send`, as `unknown_section` before composing, where `Engine::define`
  reported `missing_required_field` or `value_not_permitted` (#3030 D126,
  D154, #3342).
- A call polls its `CancellationToken` before and after each member it
  builds, at every checkpoint of each dataset's run, before each batch of
  project-function calls and, in a save, once after every file is staged and
  before the first commit, and fails as `FailureKind::Cancelled` with no
  result whenever it finds the token cancelled, where it checked the token
  only on entry; `Run::save`, `ProjectRun::save` and `Submission::save` take
  the token, a cancelled save writes nothing, `CancellationToken::with_probe`
  asks a host's probe at each poll, and a project function that raises the
  host's interrupt cancels the call, where a project run returned the
  members built until then; Python and R poll their interpreters and re-raise
  the original interrupt without returning a partial result (#3030 D46, D74,
  D186, #3260).
- `SpecRequest::stream` returns a `Streamed` run whose output a `Batches`
  reader, or the Arrow C stream it exports, produces as it is read: the first
  pull builds the run, each later one builds one batch, the token is also
  polled before each batch, and a reader dropped before its last batch cancels
  the run. `Streamed::run` gives the result through a `RunGuard`, and
  `Streamed::progress` where the run stands as a `StreamProgress`.
  `FailureKind::Stream` names a refused reader or result: `host_thread`,
  `stream_taken`, `stream_open` or `busy` (#3697).
- `EngineOptions::with_partitions(Partitions::new(rows))` runs every build
  over consecutive partitions of `rows` driver records, each partition-safe
  step one partition at a time, with the whole-table result; the token is
  also polled between partitions. A build with a step that needs the whole
  table (a window, an aggregate, a lookup or named intermediate, SELF rows or
  a project function, also in the derivations of an intermediate that drives
  rows) is refused before derivation as `engine_rejected` with `step:
  execute` and the new code `partition_global`, unless
  `Partitions::with_whole_table_fallback` runs that step over the whole input
  (#3697).
- `Partitions::by_keys(keys, rows)` divides every build's driver input into
  key-bounded partitions, which never split a group of the specification's
  leading `keys` declared keys and hold as many whole groups as fit in `rows`
  records. A window or aggregate whose grouping includes every one of those
  keys runs one partition at a time instead of being refused as
  `partition_global`; an input whose records are not grouped by those keys
  runs as one partition (#3763).
- A partitioned build whose records one step reads together cannot sit in
  one partition is refused as `partition_global`, unless
  `Partitions::with_whole_table_fallback` runs it whole: rows driven by an
  intermediate over the driver input, such an intermediate with a `unique`
  check, and a grouped row template, key grain or ODM read whose fields omit
  a partition key, or, over consecutive partitions, that shares no field
  with the others; consecutive partitions end only between runs of the
  fields those reads share (#3830).
- A partitioned build runs each partition of its driver input through
  every derivation step and drops it before decoding the next, so it holds
  one decoded partition at a time; its output keys, checks and order run
  once over every partition's rows (#3830).
- `Table::ipc` is removed: nothing in yamaa reads an Arrow IPC stream, and a
  host takes a table through `stream()` or `batches()` (#3696).
- The Arrow form of tables is the `arrow` feature, on by default: the
  re-exported Arrow types, `Table::columns`, `Table::schema`,
  `Table::batches`, `Table::stream`, `SpecRequest::stream` and its streamed-run
  types, and `InputFrame::import`, which copies a
  host frame's values into the engine's own columns where it shared their
  buffers. `info().features` lists the format features only (#3696).
