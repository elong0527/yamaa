# yamaa 1.0.0

yamaa 1.0.0 is in development. These notes are written as it is built, and
become the notes of the 1.0.0 release. The
[0.8.0 notes](https://github.com/elong0527/yamaa/blob/yamaa-v0.8.0/docs/releases/0.8.0.md)
cover the changes released before it, including the Parquet saved-output
change and concurrent execution.

## Changes

### Command line

- **The packages run the command line as themselves.** `yamaa.cli(arguments)`
  and `python -m yamaa` in Python, and `yamaa_cli(arguments)` in R, run one
  command of the `yamaa` command line over the package's own engine: a run of
  a specification that calls a project function verifies the project's lock
  and calls the functions installed in that interpreter, where the standalone
  binary refuses it as `unsupported_operation`. Each prints what the binary
  prints on the package's standard streams and returns the binary's exit
  status, and `--version` and `selftest` name the host and its version, which
  the text form prints on a `host version:` line. The commands moved from the
  binary into the facade's `cli` module, over a `Runtime` each client
  configures (D-next on #4064).
- **The standalone binary runs project functions through an interpreter's
  worker.** `yamaa run` of a project that calls project functions starts
  `python -m yamaa._worker` or the R package's worker in `Rscript`, in the
  interpreter `--interpreter` names or the one found on `PATH`, and runs the
  functions there as the package's own `run()` runs them, verifying the
  lock first. `--host python|r` names the language; without it, the one
  language the project names an `environments` entry for, or else the one
  its function files implement, runs them, and a project that names both
  runs none, as before. The run's JSON document gains `host`. The worker's
  package must carry the binary's engine version, which a declared lock's
  verification checks as `runtime_artifact_mismatch` of `yamaa`. The
  command-line conformance runs still start no worker (D-next on #4064).

### Specification language

- **A date can become a datetime at a named time of day.** `impute` with
  `type: datetime` now also takes a `date` source and supplies its time of day
  from `time: first` (`00:00:00`) or `time: last` (`23:59:59`). The result
  keeps the date's collected precision, so the time imputation flag reads `H`.
  A date still never converts to a datetime implicitly (TIME-8, VALUE-18,
  #4270 D-next).
- **A row failing before its template's filter says so.** When one of a row
  template's own derivations fails on a candidate row whose keys are all
  derived, before the template's `filter` runs, the finding's context names
  that filter as `template_filter`, and a `missing_input` finding explains
  that the filter runs only after the row's derivations (COLUMN-9, #4272
  D-next).
- **A one-record table is read without a join key.** A named intermediate may
  write `key: none`, so every row reads every record of its dataset: one record
  is read by every row, none gives the absence answer, and several fail as
  `multiple_matches` unless `keep` chooses one. A study-level settings table
  no longer needs a constant column derived on both sides to join on. An
  intermediate `key` written as a bare string other than `none`, such as
  `key: USUBJID`, now fails as `value_not_permitted` rather than
  `invalid_field_type` (LOOKUP-5, #4271 D-next).
- **A refused read of a driver's derived field names its remedy.** A
  column-level derivation that reads a field a row-driving intermediate
  derives is still refused as `unsupported_operation`, and its context now
  carries a `hint`: derive the field into a column in each row template the
  intermediate drives, then read that column (ROW-2, #4269 D-next).
